# ESP32 SAPI

Браузерний клієнт MQTT SAPI-каналу (`docs/mqtt-web-handoff.md`, фаза 1/2).
Одна статична сторінка (`index.html`), нуль build-кроку, нуль залежності від
цього репо під час виконання — підключається напряму до MQTT-брокера
(WebSockets), без жодного HTTP-запиту до плати.

**Не частина прошивки.** `pio run` цю теку не бачить (поза `src/lib/include`),
не потрапляє в LittleFS-образ веб-порталу. Живе в монорепо свідомо (розділ
"Монорепо" сесії, `docs/mqtt-web-handoff.md`) — контракт (топіки, JSON-shape)
і сторінка, що його споживає, ще активно змінюються синхронно.

## Запуск

Будь-який статичний http-сервер із цієї теки, напр.:
```
python3 -m http.server 8765
```
і відкрити `http://localhost:8765/`.

## Підключення

Форма підключення (host/port/prefix/username/password/client-id) —
`localStorage` цього браузера, нічого не передається нікуди, крім самого
брокера. Кредеші для конкретного пристрою — `docs/mqtt-web-handoff.md`,
розділ "storage-шар" (п.8): rpi5, окремий WS-listener (`9001`), окремі
`sapi_passwd`/`sapi_acl`, один статичний акаунт на пристрій
(`sapi-<client-id>`, read-only на `devices/<client-id>/#`, write на
`.../api/+` + `.../api/ecoflow-params/+` для per-device drill-down на "Raw
parameters", і write `command/<client-id>` + read `command/<client-id>/reply`
для вкладки Commands, сесія 2026-09-26 — розворот попереднього рішення "без
`command/`", `docs/mqtt-web-handoff.md`).

Форма — попап під індикатором стану в правому верхньому куті (клік
відкриває/закриває, `Escape`/клік поза попапом закриває). Вкладки
System/Wi-Fi/EcoFlow/MQTT/Log видно лише під час активного з'єднання.
Чекбокс "Auto-connect on load" (дефолт — вимкнено) — конектитись самостійно
на завантаженні сторінки, якщо є збережені `host`+`client-id`; під активним
з'єднанням уся форма readonly (спершу Disconnect, тоді редагувати).

## System — компонує кілька відповідей в один набір карток

`renderSystemInfo()` (`render.js`) не показує лише сирий `system-info` —
Device/Memory/NVS/Flash з нього, але Network/EcoFlow/MQTT-картки читають
ОСТАННЮ відому відповідь `wifi-status`/`ecoflow-status`/`mqtt-status`
(`index.html`: `lastWifiStatus`/`lastEcoflowStatus`/`lastMqttStatus`,
`renderSystemPanel()` перемальовує System на будь-яку з 4 відповідей, не
лише на власний `system-info`-полл) — той самий підхід, що й HTTP-портал
(`assets/www/index.html`: одна відповідь малює і власну вкладку, і
System-картку). Поля, яких жодна команда ще не несе (LittleFS/SD-стан,
частина Device-картки без `HAS_WEB_PORTAL`-контексту) — `mockDl()`/`***`,
не нуль і не пропущений рядок.

Memory-картка має бар використання heap (Used/Largest free block/Free
фрагментоване, маркер Min free ever) — новий SAPI-специфічний віджет,
якого немає на самому HTTP-порталі, з hover-tooltip на кожному сегменті
окремо (не один загальний на весь бар).

## Wi-Fi — Status + Saved profiles, 1:1 з порталом

`renderWifiStatus()` (`render.js`) — двоколонковий каркас `.cols`/`.col`
(той самий, що вкладка Commands — DRY, не другий CSS-словник під ту саму
розкладку): Status зліва, Saved profiles справа. Таблиця Saved profiles —
буквальний порт `renderProfiles()` з HTTP-порталу (SSID + бейджі
open/static/connected, Priority, Signal, State), з останньою колонкою —
кнопкою "Connect", але **заблокованою** (`disabled`, з `title`, чому): SAPI
поки не має жодної команди, що міняє стан пристрою (розділ "Пре-альфа"
нижче). Порожню колонку без цього якоря таблиця виглядала б "стисло" —
Signal/State без фіксованої ширини (на відміну від Priority, `num`) вільно
розповзаються по всій ширині `.col`, і саме кнопка праворуч дає рядку край,
до якого є сенс тягнутись. Коли з'явиться мутуючий канал на MQTT — кнопка
розблокується (не інша розмітка). Немає й "Networks in range"/Actions
(Scan/Reconnect/Hotspot) — ці блоки порталу наповнює лише сама мутуюча дія,
якої тут іще немає.

Saved profiles — окрема команда `wifi-connections` (не поле `wifi-status`):
список профілів у NVS міняється рідко (лише мутацією), тому не варто ганяти
його в кожній відповіді `wifi-status`. Запит поза `COMMANDS`/`panels[cmd]`
(той самий підхід, що `ecoflow-journal` нижче) — `requestWifiConnections()`
викликається разом із кожним запитом `wifi-status` (Refresh, auto-тик,
перший запит при конекті), а не власним контролом: портал теж підвантажує
`/api/wifi/connections` разом зі статусом Wi-Fi-вкладки, не окремою кнопкою.

## MQTT — Connection + Console mirror + legend, 1:1 з порталом

`renderMqttStatus()` (`render.js`) — той самий каркас вкладки MQTT HTTP-порталу
(`assets/www/index.html` `#tab-mqtt`): **Connection** (dl зі статусом брокера,
dropped out/in, LWT трьома рядками, Heartbeat двома), **Console mirror**
(окремий h2 + той самий `p.muted` про `console-mqtt`), і `dl.legend` унизу
(Dropped / Subscribe denied / Commands rejected). Без темної коробки `.out`
навколо вмісту — як Wi-Fi. AUTO/Refresh лишаються в шапці секції (SAPI
опитує MQTT-командою; портал ходить на `/api/mqtt/status` сам). Компактна
System-картка MQTT не змінюється (`mqttSystemRows()`).

## LittleFS — картка System + вкладка Files

Картка LittleFS у System тепер реальна: `system-info` несе `littlefs`
(`WebSystemModule::littleFsJson()` — той самий форматер, що `/api/system/info`
порталу) → Total/Used/Free + бар «використано / вільно» (`usageBarHtml()`,
ті самі `.heap-bar*` стилі, що Memory). Той самий бар (heap-версія і
LittleFS-версія) додано й на вкладку System веб-порталу.

Вкладка **Files** — окремий запит `fs-list` з аргументом `path` (поза
`COMMANDS`, як `wifi-connections`): порт лівої колонки Files порталу — крихти,
лічильник з місткістю, таблиця Name/Size, клік по каталогу відкриває його.
**Preview** — порт переглядача порталу: View (або клік по рядку файла) тягне
вміст командою `fs-read` шматками по 3 КБ (base64; перший шматок послідовно, решта по 2 запити одночасно — межа
`SAPI_MAX_INFLIGHT`; відповідь `busy` повторюється), після чого та сама логіка, що на порталі: текст → UTF-8, бінарник
→ hex-дамп, зображення → `<img>` (blob URL). Стеля для тексту/hex — 256 КБ (`FS_PREVIEW_MAX`,
решта позначається «first X of Y»); зображення тягнуться цілком (обрізаний
JPEG — сіра смуга), запобіжник `FS_IMAGE_MAX` = 1 МБ; понад 64 КБ питає `confirm()`. Стан
Preview лежить поза DOM — переживає перемальовку списку.
Редактор, New file/folder, Download/Rename/Delete — мутації, яких SAPI не
робить: заблоковані з `title` (як Connect у Wi-Fi). Refresh перечитує
поточний каталог.

## EcoFlow — "Raw parameters" на вимогу (drill-down)

Агрегат `ecoflow-status` свідомо не несе сирі `params` кожного пристрою
(розмір payload) — картка пристрою показує кнопку "Load raw parameters"
(`render.js`: `ecoParamsSection()`), яка публікує окремий запит у
`devices/<client-id>/api/ecoflow-params/<sn>` (`index.html`:
`requestEcoflowDeviceParams()`). Після відповіді кнопка стає "Refresh" (той
самий клас `.eco-params-btn`, той самий делегований клік) — параметри
пристрою змінюються в часі, тому одноразового завантаження недостатньо.

На час очікування відповіді весь блок `<details class="eco-params">`
(не лише кнопка) отримує `.busy` — буквальний порт `.busy`/`setBusy()` з
HTTP-порталу (напівпрозорий шар + спінер, кнопка всередині `disabled`).
Явний timeout (`ECO_PARAMS_TIMEOUT_MS`, 10с) знімає `.busy` й логує помилку
в Log-вкладку, якщо пристрій так і не відповів — на відміну від порталу
(там `job()`/`finally` навколо проміса HTTP-запиту), тут відповідь
асинхронна через окрему MQTT-подію, тож "завершення" — це або вона, або сам
таймер.

## EcoFlow — Journal (журнал переходів grid, окремий запит)

Свій блок `<details id="eco-journal-wrap">` під картками пристроїв
(`render.js`: `ecoJournalSection()`) — окрема команда `ecoflow-journal`,
**не розширення `ecoflow-status`**: злитий хронологічний потік
`Transition`-переходів grid, той самий провайдер
(`EcoflowJournalView.hpp`), що серійна команда `ecoflow-journal show` і
HTTP-роут порталу `GET /api/ecoflow/journal`. Перша команда фази 1 з
реальним `args` у тілі запиту (`{"id":N,"args":{"target":"all"|"<sn>"}}`) —
"target" не topic-per-device (як `ecoflow-params/<sn>`), бо запит рідкісний,
а не частий per-device polling.

Вибір пристрою — `<select>` над таблицею ("All devices" + по одному на
кожен з останньої відповіді `ecoflow-status`, той самий знімок, другого
запиту під список не заводимо). Найновіший перехід кожного пристрою
(`mark===">"`, стан ще триває) і останній повністю завершений інтервал
(`mark==="<"`) підсвічені смугою зліва (CSS custom property `--eco-stripe`,
`ecoJournalRow()`) плюс текстова приписка "(ongoing)"/"(closed)" —
візуальний аналог міток `>`/`<` серійної команди, колір сам собою непомітний
для дальтоніків. Колір смуги — той самий, що в колонці Grid
(`ecoGridColorVar()`: on-grid зелений/off-grid жовтий/невідомо сірий), а не
фіксований зелений; попередній стан — той самий колір, приглушений
(`--*-dim`, 40% альфа), а не перефарбований у сірий.

Клік по рядку підсвічує один пристрій — буквальний порт того самого жесту
на порталі (`assets/www/index.html`): клікнутий рядок і всі рядки того самого
`row.device` отримують `class="selected"`, решта — `class="muted"` (CSS:
`opacity`, а не сторінковий `.muted`-колір тексту — смуга `--eco-stripe`
лишається видимою й приглушеною разом з текстом). Повторний клік по вже
обраному знімає виділення повністю. На відміну від порталу (там `tbody`
оновлюється точково, і клас на рядок додає DOM-мутація ПІСЛЯ вставки) тут
увесь `#tab-ecoflow` перемальовується з даних щоразу, тому `ecoJournalRow()`
одразу вставляє клас у розмітку рядка, а обраний пристрій зберігається як
атрибут `data-eco-selected` на самому `#eco-journal-wrap` — той самий "скан
DOM ПЕРЕД `innerHTML=`" підхід, що для `journalTarget`/`journalAuto`/
`journalOpen` нижче. **`ecoJournalSection()` мусить писати цей атрибут назад
у згенерований `<details>`** — без цього кожна наступна перемальовка (тик
`ecoflow-status`, а не лише сам журнал) повертала б вузол без атрибута, і
виділення губилось би вже на другому рендері після кліку, а другий клік по
тому самому рядку взагалі не знімав би підсвітку (порівняння з `undefined`
завжди хибне).

Порядок рядків — чекбокс "newest first" (`#eco-journal-newest-first`, за
замовчуванням увімкнено), той самий принцип, що на вкладці Log
(`#log-newest-first`). На відміну від Log, тут немає окремого шару
"порядок зберігання"/"порядок показу" — `journalData.rows` і так
перебудовує весь `<tbody>` при кожному рендері, тому чекбокс лише реверсить
копію масиву перед `.map(ecoJournalRow)` (`ecoJournalSection()`); сервер
завжди віддає rows хронологічно (найстаріший перший), `row.mark` — властивість
самого рядка, не позиції, тож reverse() нічого не ламає. Зміна чекбокса не
шле нового MQTT-запиту — лише перемальовує вже наявні дані
(`renderEcoflowPanel()`). На відміну від Log, стан не персистується в
localStorage — той самий (сесійний, лише DOM) рівень, що вже мають
`#eco-journal-auto`/вибраний пристрій/розгорнутість/підсвічений кліком
пристрій.

Запит іде: розгортання `<details>`, зміна вибраного пристрою, клік
"Refresh", і, за бажанням, галочка "auto" (низький пріоритет, окремий
таймер 5с, не пов'язаний із `COMMANDS`/backoff-механізмом чотирьох
агрегатів). Розгортання ловиться кліком по `<summary>` (перевірка `.open`
ДО застосування власної activation behavior браузера — стан ще "закрито"
означає "цей клік ось-ось розгорне"), **не подією `toggle`**: увесь `#tab-
ecoflow` перемальовується цілком (`innerHTML=`) на кожен `ecoflow-status`,
а щойно вставлений у DOM `<details open>` сам по собі шле `toggle` (відомий
"фічабаг" Chromium) — з подією замість кліку журнал розгортався б один раз
і далі сам себе перезапитував без паузи назавжди. `.busy` на весь блок і
явний timeout (`ECO_JOURNAL_TIMEOUT_MS`, 10с) — той самий підхід, що "Raw
parameters" вище, лише запит один на раз (не по одному на пристрій), —
**окрім самого тика "auto"**: `requestEcoflowJournal(target, auto=true)`
пропускає `setEcoJournalBusy(true)`, інакше оверлей+спінер на весь блок
блимав би щоразу, коли швидка відповідь приходить сама, без дії
користувача. Примусові шляхи (розгортання, зміна пристрою, "Refresh")
`.busy` лишають — там користувач щойно клікнув і чекає на відгук.

## Log — Pause/Resume, Newest first, кореляція запит/відповідь

Кожна MQTT-подія — один DOM-рядок (не суцільний текстовий блоб), pretty-
друк JSON лише по кліку. Запит і відповідь з тим самим `id` зводяться в
ОДИН рядок. **Pause/Resume** (кнопка в шапці вкладки) зупиняє лише запис
нових рядків — сам MQTT-трафік і обробка команд ідуть незалежно; події під
час паузи пропускаються, не буферизуються. **Newest first** (чекбокс) —
порядок показу, окремий від порядку зберігання.

## Commands — довільна команда через `command/<id>`, 1:1 з порталом

Вкладка Commands: список зареєстрованих serial-команд ліворуч (JSON API
`commands-list`, дзеркало `/api/commands/list` порталу — окремий одноразовий
запит поза `COMMANDS`, не auto-poll), поле Run + панель Output справа,
Shortcuts із drag-n-drop сортуванням. На відміну від решти вкладок SAPI,
запуск команди йде через `command/<client-id>` (текстовий канал, спільний із
serial/cron), не через структурований `devices/.../api/<cmd>` — свідомий
розворот раннього рішення "SAPI без `command/`"
(`docs/mqtt-web-handoff.md`, розділ «SAPI: вкладка Commands»), за проханням
користувача.

**"Виконано" тут — евристика тиші по reply-топіку, не факт протоколу.**
`command/<id>` не несе кореляційного `id`, і порожня фінальна порція, якою
`CommandResponse::finish()` міг би сигналізувати кінець, до MQTT не
доходить (`MqttReplyTarget::deliver()` відкидає `length == 0`). Панель Output
показує `running: <cmd>` до 2с тиші на reply-топіку → `no more output for
2s: <cmd>`, зі страховкою 60с (як `CAPTURE_TIMEOUT_MS` порталу), якщо
відповіді не було взагалі.

**Shortcuts — `localStorage` (`sapi.commandShortcuts.v1`), не NVS пристрою.**
SAPI не має шляху писати у flash пристрою (лише MQTT-запити з allowlist),
тому shortcuts — зручність ЦЬОГО браузера, той самий принцип, що форма
підключення. Перетягування сортує список одразу в localStorage, без
мережевого проміжку.

## Пре-альфа — жорстко зашитий allowlist (System/Wi-Fi/EcoFlow/MQTT)

`COMMANDS` у `index.html` — той самий список, що в `src/main.cpp`
(`kJsonApiSystemInfo`/`kJsonApiWifiStatus`/`kJsonApiEcoflowStatus`/
`kJsonApiMqttStatus`) - керує лише auto-poll вкладками System/Wi-Fi/EcoFlow/
MQTT, НЕ вкладкою Commands (та своя, поза цим списком - розділ вище).
`kJsonApiWifiConnections`/`kJsonApiEcoflowJournal`/`kJsonApiCommandsList` теж
поза `COMMANDS` — той самий принцип, що весь цей розділ: одноразові/рідкісні
запити всередині вже наявної вкладки (Wi-Fi/EcoFlow/Commands), не власна
панель. Коли з'явиться discovery-маніфест (фаза 2), він замінить цей список
UI, що будується з даних брокера, а не з коду тут.

**Read-only — жодна з команд не міняє стан пристрою.** Ні `COMMANDS`, ні
одноразові запити вище не мутують NVS/WiFi/EcoFlow: SAPI показує Wi-Fi (разом
зі Saved profiles) так само, як портал, але без Actions (Scan/Connect/
Reconnect/Hotspot) і без форми профілю — рішення сесії, коли ставилась ця
вкладка (додавання мутуючих JSON API команд — окремий крок, не цей).

## Рендер і тест

`render.js` — чисті функції рендера (`renderSystemInfo`/`renderWifiStatus`/
`renderEcoflowStatus`, без DOM), винесені з `index.html` окремим файлом саме
для того, щоб той самий код можна було прогнати headless у Node:

```
node sapi/test/render.test.js
```

Тест — без test-раннера (у проєкті його ще нема, `docs/tech_debt.md`),
голий Node + `assert`, фейл — ненульовий exit code. Покриває щасливий шлях і
крайові випадки (відсутній `ap`, порожні `devices`, `nvs.available=false`,
`null`-поля, XSS-екранування) на реальній формі JSON з живого тесту в
браузері. Не перевіряє CSS/layout — лише що прийде в `innerHTML`.

## Правило: контрол сторінки переживає refresh/reconnect

**Будь-який чекбокс чи перемикач, що керує ВИГЛЯДОМ або поведінкою
сторінки** (не даними з'єднання — ті вже в `localStorage` окремо,
`STORAGE_KEY`/`loadConn()`) — «Auto» кожної команди, «Newest first»,
Pause/Resume логу, і будь-який майбутній подібний контрол — має пережити
перезавантаження сторінки й повторний конект, а не тихо скидатись до
дефолту щоразу. Занотовано за проханням користувача (сесія 2026-09-24),
після третього такого контролу (Pause/Resume) поспіль — той самий момент,
коли в проєкті вже узагальнюють («другий користувач — привід узагальнити»,
`CLAUDE.md`, KISS).

Механізм — `index.html`, один спільний ключ `sapi.uiToggles.v1`
(`loadUiToggles()`/`saveUiToggle()`), не по одному `localStorage`-ключу на
контрол:

- **Чекбокс** — додати `data-persist="<унікальний-ключ>"` у розмітку (чи
  виставити `el.dataset.persist` програмно, як для `.auto-toggle`, де ключ
  іде з імені команди) — підхоплюється автоматично циклами
  `wirePersistentCheckbox`/`applyPersistedToggles()`, без правок коду.
- **Не-чекбокс** (кнопка-перемикач на кшталт Pause/Resume) — окремий
  `setXxx(value)`-сеттер (той самий, що й для кліку користувача — одна
  функція, не дві копії логіки) + власний виклик
  `saveUiToggle('xxx', value)`/`loadUiToggles()` поруч у
  `applyPersistedToggles()`.

**Пишемо одразу на зміну, читаємо лише при `connected`** (`client.on(
'connect', ...)`), не при завантаженні сторінки — контроли на кшталт «Auto»
без живого MQTT-клієнта однаково нічого не запустили б, і одне правило "коли
відновлюємо" для всіх контролів простіше за різний момент для кожного.
Відновлення — через `dispatchEvent(new Event('change'))` на вже наявному
чекбоксі, не дублювання його change-логіки в іншому місці (DRY).
