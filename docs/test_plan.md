## 0. Підготовка

### 0.1 Передумови

- `secrets.ini` у корені (не в git). Мінімум: `wifi_ssid`, `wifi_password`, `mqtt_host`,
  `mqtt_port`, `mqtt_client_id`, `mqtt_lwt_topic`, `mqtt_topic_prefix`.
  `mqtt_client_id = "mqtt-${PIOENV}"` і `mqtt_lwt_topic = "devices/${PIOENV}/status"` —
  ідентичність плати підставляється автоматично з імені env.
- Брокер MQTT доступний, і є `mosquitto_sub` / `mosquitto_pub` на робочій машині.
- Порт пристрою. У проєкті вже траплялись обидва варіанти: `/dev/ttyUSB0` (USB-UART:
  `esp32-st7789`, `ttgo-t1`, `esp8266`) і `/dev/ttyACM*` (native USB CDC: обидві C6, `esp32-c3`,
  S3-плати). На C3, як і на обох C6, це USB-Serial/JTAG, тому в env стоять
  `monitor_rts = 0` / `monitor_dtr = 0`: без них відкриття порту ресетить плату.

### 0.2 Команди

```bash
export ENV=esp32-c6-lcd096          # ім'я environment
export PORT=/dev/ttyACM1            # порт пристрою

# прошивка + монітор
pio run -e $ENV --upload-port $PORT --monitor-port $PORT -t upload -t monitor

# файлова система (LittleFS) - ОКРЕМА команда, не робиться разом з upload
pio run -e $ENV --upload-port $PORT -t uploadfs

# лише монітор
pio device monitor -p $PORT -b 115200
```

**Одноразові команди — через `./esp`, а не монітор.** Він відкриває порт БЕЗ дотику до
DTR/RTS, тому плата **не ресетиться** і стан у RAM зберігається; `pio device monitor`
ресетить навіть із `monitor_dtr=0`/`monitor_rts=0`.

```bash
./esp ecoflow                  # порт визначається сам
./esp $ENV heap                # або за іменем env
./esp /dev/ttyACM0 status sd   # або за явним портом
ESP_TIMEOUT=30 ./esp status sd+   # для довгих відповідей
```

Індекс для IDE — `./compiledb <env>` (env обов'язковий: індекс містить прапорці саме тієї
плати). Деталі обох скриптів — `docs/architecture.md`, розділ «Інструменти в корені
репозиторію».

`uploadfs` обов'язковий для плат із `LITTLEFS_BACKGROUND_IMAGE` (4848s040, s3-lcd147, c6,
c6-lcd096) і для тесту `dump-asuswrt` (читає `/asus-get_clientlist.json`).

> ⚠️ **`data/` містить не лише асети.** Разом із зображеннями на пристрій заливаються
> `convert` (скомпільований бінарник, 148 KB), `stb_image.h` (276 KB), `convert.c`,
> `convert.py`, `FloatPixel.hpp` — разом ~476 KB, тобто ~40 % розділу LittleFS на платах
> з 1.5 MB spiffs (`esp32-st7789`, `esp32-c6-lcd096`). Перед `uploadfs` варто або тимчасово
> прибрати їх із `data/`, або перенести конвертер у `tools/` назавжди.

### 0.3 Базовий MQTT-моніторинг (тримати відкритим під час усіх мережевих тестів)

```bash
# <prefix> - значення mqtt_topic_prefix; на пристрої його показує команда `dump-mqtt`
mosquitto_sub -h <broker> -p 1883 -t "<prefix>/#" -v \
  -F "@Y-@m-@d @H:@M:@S [q@q/r@r] %-50t %p"
```

Відповіді на команди приходять у цю ж підписку (`<prefix>/command/mqtt-<env>/reply`), але
вони багаторядкові й у спільному потоці читаються погано. Для блоку **M** зручніше тримати
поряд другий термінал лише з reply-топіком і **без** `-F`, щоб рядки виводились як є:

```bash
mosquitto_sub -h <broker> -p 1883 -t "<prefix>/command/mqtt-$ENV/reply"
```

Для блоку **M20–M27** (дзеркало консолі) потрібен ще третій термінал — теж без `-F`,
бо там потік рядок-у-рядок і будь-який префікс лише заважає звіряти його з
`./esp`-монітором:

```bash
mosquitto_sub -h <broker> -p 1883 -t "<prefix>/console/mqtt-$ENV"
```

## 2. S — Smoke (усі плати)

| # | Дія | Очікуваний результат |
| :-- | :--- | :--- |
| S1 | Прошити, відкрити монітор, натиснути RESET | Банер `*-*-*-...`, рядок з моделлю чипа і `(<PIOENV>)`, далі послідовність `... setup done`, наприкінці `> Ready. Enter 'list' for comand list.` |
| S2 | Дочекатись 60 с без дій | Жодних reset/panic/`Guru Meditation`, `Stack canary`, `Task watchdog` у консолі |
| S3 | `list` | Список команд. Обов'язково присутні: `list`, `status`, `reboot`, `scan`, `flip`, `led`, `clock`, `brightness`, `dump-mqtt`, `publish`, `mqtt-prefix`, `dump-asuswrt`; на платах із Gmail — ще й `mailto`, `sendmail`, `smtp-probe` |
| S4 | `status sys` | Секція `ESP32 CHIP INFO`: модель чипа, ревізія, ядра, частота, SDK, Core, розмір і швидкість флеш, купа, PSRAM, WiFi SSID/RSSI, IP, `Last Reset Reason`, `display.brightness` |
| S5 | `zzz` (неіснуюча команда) | `Unknown command: zzz` — **саме текст команди**, не сміття й не порожньо *(регресія R3)* |
| S6 | `status` без аргументу | Підказка `use: status sys\|cfg\|sd\|sd+\|flash\|flash+\|littlefs` |
| S7 | `reboot` | `[SystemReset] Rebooting...`, пристрій стартує заново; після старту `status sys` показує `Last Reset Reason: Software reset (ESP.restart)` |
| S8 | Ввести рядок довший за 128 символів без `\n`, потім Enter | `command too long, buffer vanished`, пристрій живий |

Актуальний префікс і стан з'єднання показує `dump-mqtt`. Нижче `<prefix>` = `mqtt_topic_prefix`,
`<env>` = ім'я environment.

### Відповідь на команду (request-response)

Механізм — `ScopedLogCapture` + `lib/CommandResponse`; опис і пастки в
`docs/architecture.md`, розділ «Request-response для команд». Тримати відкритим
reply-підписника з розділу 0.3.

| # | Дія | Очікуваний результат | Плати |
| :-- | :--- | :--- | :--- |
| M12 | `mosquitto_pub -t "<prefix>/command/mqtt-<env>" -m "heap"` | В `<prefix>/command/mqtt-<env>/reply` приходить **одне** повідомлення: перший рядок `[I][cmd.reply] > heap`, далі рядки `heap` рівно в тому вигляді, що в моніторі (той самий префікс `[I][heap   ]`). Ті самі рядки паралельно в `./esp`-моніторі — консоль не «вкрадено», це дублювання, а не перенаправлення | усі |
| M13 | Те саме з `-m "list"` (десятки рядків) | Повідомлення підряд: до 8 порцій тексту (`COMMAND_RESPONSE_MAX_CHUNKS`) плюс **окреме** коротке фінальне з `...(truncated, N more lines)` — тобто 9 максимум. **Жоден рядок не розрізаний посередині** — порція рветься лише по `'\n'`, поки в буфері гарантовано влазить наступний рядок логу | усі |
| M14 | Те саме з `-m "dump-mqtt"` — команда, у якій логує сам MQTT-клієнт | Одна відповідь і тишина. Нескінченний потік у reply-топік = зламався re-entrancy guard у `CommandResponse::flushChunk()`: рядки доставки потрапляють у відповідь, яку вони ж доставляють | усі |
| M15 | Запустити `ecoflow-sync` (REST крутиться у власному таску `ecoflow-rest`) і **під час** нього надіслати `-m "heap"` | У відповіді немає **жодного** рядка з тегом `ecoflow`, хоч у консолі вони йдуть упереміш. Захоплення прив'язане до `TaskHandle_t`, а не глобальне; поява чужих рядків = регресія в `LogCaptureRegistry` | ttgo-t1, c6, c6-lcd096, c3 |
| M16 | Тимчасово `-D COMMAND_RESPONSE_MAX_CHUNKS=2`, перезібрати, повторити M13 | 2 порції тексту + третє повідомлення з маркером; N у маркері помітно більше, ніж у M13. **Повернути 8** | одна плата |
| M17 | `smtp-probe 587`, потім `smtp-probe 465` | Обидва дають `greeting: 220 smtp.gmail.com ESMTP …`: 587 — по відкритому TCP, 465 — через TLS ядра (`WiFiClientSecure`). Це перевірка мережі, порту й mbedTLS **без** поштової бібліотеки: якщо банери є, а `sendmail` усе одно падає — винна бібліотека, не плата. Заміряно на c6-lcd096: конект 51 мс / handshake 430 мс | плати з Gmail |
| M18 | `mailto <address> heap`, далі `dump-mqtt` | У консолі: `[I][cmd.reply] > heap` (луна **вкладеної** команди, не самого `mailto`), вивід `heap`, `[D][reply.mail] MQTT suspended for SMTP session`, `[I][gmail] connecting to <host>:465 (implicit SSL), … B free`, потім `[I][gmail] sent to <address>`, `session closed, … B free` і `isConnected = yes`. **Лист має прийти** — перевірити скриньку: тема `<env>: heap`, тіло — той самий вивід, що в консолі | плати з Gmail |
| M19 | `sendmail`, дивитись на таймінги | Попередження `sending test mail to … - blocks this task` іде **до** паузи; уся сесія (конект → `sent to` → `session closed`) укладається в кілька секунд. Заміряно на c6-lcd096: 1.6 с до `sent`, 3.6 с разом із закриттям. Пауза на десятки секунд або тиша після `sent to` = регресія: десь повернувся блокуючий режим ReadyMail (його внутрішній таймаут читання — 120 с) | плати з Gmail |

### Дзеркало консолі (`console-mqtt`)

Механізм — `LogMirror` + `lib/ConsoleMqtt`; опис і пастки в `docs/architecture.md`,
розділ «Дзеркало консолі в MQTT». Тримати відкритим третього підписника:
`mosquitto_sub -h <host> -t '<prefix>/console/mqtt-<env>' -v`.
Тільки 7 ESP32-плат — на `esp8266` механізм вирізано з прошивки.

| # | Дія | Очікуваний результат | Плати |
| :-- | :--- | :--- | :--- |
| M20 | `console-mqtt` одразу після старту | `mirror = off, topic = '<prefix>/console/mqtt-<env>'`, лічильники по нулях, три вбудовані `deny (built-in)` і `(no user rules …)`. У підписнику тиша | ESP32 |
| M21 | `console-mqtt on`, далі кілька довільних команд | У підписнику ті самі рядки, що в `./esp`-моніторі, разом із префіксом `[I][tag    ] ` і **без** хвостового переносу (порожніх рядків між повідомленнями немає). Затримка до ~100 мс — мережевий таск дренажить чергу раз на `vTaskDelay(100)`; порядок рядків збережений | ESP32 |
| M22 | Не вимикаючи дзеркала, `reboot` при живому підписнику | Рядки старту (до конекту MQTT) **не приходять** — ні із затримкою, ні пачкою. Прихід пачки = хтось завів буфер, чого тут бути не має | ESP32 |
| M23 | `console-mqtt deny \[ecoflow`, потім `ecoflow-sync` | Рядки з тегом `ecoflow` зникли з топіка, у консолі лишились. `console-mqtt clear deny` → повернулись | c6, c6-lcd096, c3, ttgo-t1 |
| M24 | `console-mqtt allow ^\[[EW]\]` | У топік ідуть лише `[E]` і `[W]`. `console-mqtt test [I][app    ] hello` → `blocked`, `console-mqtt test [W][app    ] hello` → `pass`. Після `console-mqtt clear allow` потік відновився (порожній whitelist = пропускати все) | ESP32 |
| M25 | `console-mqtt deny [unclosed` | Зрозуміла помилка від `regerror()` (`rule '[unclosed' rejected: …`), правило **не** додане (`console-mqtt` його не показує), потік не зламався | ESP32 |
| M26 | `console-mqtt on`, далі флуд як у M11 одночасно з важкою командою | У консолі **не** має бути `[MQTT] queue overflow, dropped: N incoming` — інакше не працює `setEchoIgnoreTopic()` і пристрій сам собі забиває вхідну чергу. У топіку `console/…` не має бути нескінченного потоку: вбудоване `\[MQTT\]` зрізає рядки, породжені власною ж доставкою. Допускається `rate limit dropped N lines…` раз на 30 с | ESP32 |
| M27 | Під `console-mqtt on` надіслати MQTT-команду `heap` | У `command/…/reply` — рівно вивід команди (як M12), у `console/…` — увесь потік. Поява чужих рядків у reply = зачепили `LogCaptureRegistry`: два механізми мають лишатись незалежними | ESP32 |

**Стек і флеш** (робити при зміні правил або лімітів, а не щоразу):
`console-mqtt deny took [0-9]{3,}ms`, 10 хв роботи під навантаженням, далі
`dump-mqtt` — запас стека мережевого таска не має просісти нижче ~4 КБ із 8
(`regexec()` виконується в **кожному** таску, що логує). Приріст прошивки після
введення механізму заміряно: ESP32 — 28…32 КБ (`esp32-c6`: 1 908 640 → 1 940 320,
вільно 156 832), `esp8266` — 48 Б.

## 14. Особливості й ризики по платах

### 14.1 `esp32-4848s040` (ESP32-S3, 480×480, RGB-панель)
- Єдина плата з `DISPLAY_SPLIT_COUNT=1` при 480×480 — спрайт на весь кадр це 460 KB, живе
  **тільки** завдяки OPI PSRAM. У `status sys` перевірити `PSRAM found: YES`, інакше дисплей
  не ініціалізується.
- Touch GT911 — повний блок **T**.
- Найважчі ефекти (I3): 480×480 × radius 8 × 3 passes. Це найкращий стрес-тест на watchdog.
- Кнопки немає (`FLIP_BUTTON_PIN` не заданий) — блок **B** пропустити, крім B3.

### 14.2 `esp32-s3-lcd147` (ESP32-S3, 172×320)
- SD через **SD_MMC 4-bit**, не SPI. `status sd` іде через `SDCardInspector::printAll(SD_MMC, …)`.
  Якщо картка не визначається — перевіряти саме `SD_MMC.setPins()` у `setupSD()`, а не SPI-піни.
- `TOUCH_CS=0` у build_flags — це заглушка проти warning'а TFT_eSPI, touch немає.

### 14.3 `esp32-st7789` (ESP32, 240×320)
- **Єдина плата з light sensor** — блок **L** тільки тут, і саме тут перевіряється C4 (NVS wear).
- **Єдина плата з вбудованим фоном** (`BACKGROUND_IMAGES_COUNT=1`): фон із PROGMEM, команд
  ефектів немає. Блок **I** — лише перевірити, що фон видно.
- `DISPLAY_SPLIT_COUNT=6` — найдрібніше розбиття, найкращий кандидат на перевірку D7.
- SD на **400 kHz** (`SD_FREQ=400000`) — лістинг великої картки буде помітно повільним, це не баг.
- Gmail (`ReadyMail`) тут не підключений.

### 14.4 `ttgo-t1` (ESP32, LilyGO T-Display 135×240)
- Найпростіша конфігурація: без SD, touch, сенсора, фону. Фактично перевіряє «спільне ядро»:
  дисплей + WiFi + NTP + MQTT + консоль.
- `BACKGROUND_IMAGES_COUNT=0` і без `LITTLEFS_BACKGROUND_IMAGE` → `drawBackgroundImage()`
  щокадру робить `display.clear()`. Якщо помітне мерехтіння — це очікувана поведінка цієї
  конфігурації, а не регресія.
- `upload_speed = 115200` (навмисно) — прошивка помітно довша.
- **EcoFlow тут увімкнено** (`HAS_ECOFLOW_CLIENT=1`) і перевірено на залізі — попри те, що
  це «найпростіша» плата. Блок **E** проходити повністю. Умова для нього — PicoMQTT
  (пауза TLS-сесії `MqttClient::suspend()` є лише в цій гілці), а не наявність C6.
- ⚠️ **Відома проблема: рвана консоль.** Під час WiFi-активності (`scan`, MQTT) у Serial
  трапляються обрізані рядки, зниклі рядки і биті байти (`������`). Перевірено, що це **не**
  код: `logstat` показував `dropped=0`, а команда `history` віддає ті самі рядки **цілими** —
  тобто вони формуються правильно і псуються вже на лінії. Найімовірніша причина — просадка
  живлення під піковим споживанням радіо (тонкий кабель / слабкий USB-порт), далі — наведення
  на USB-міст. **Не шукати причину в логері.** Перевірка, якою це було встановлено, —
  команда `history`, але вона зараз недоступна (див. пункт нижче); щоб повторити перевірку,
  доведеться тимчасово ввімкнути `SCREEN_LOG_TAIL_LINES`.
- ⚠️ **Буфер історії тут поки вимкнено** (`SCREEN_LOG_TAIL_LINES=0`, як і в решті 7 env),
  тому команди `history` **немає в жодній збірці** — не шукати її в `list`. Ця плата
  лишається кандидатом номер один на її ввімкнення: саме тут рвана консоль відтворюється
  стабільно. Щоб отримати `history`, поставити в env `-D SCREEN_LOG_TAIL_LINES=50` і
  перепрошити.

### 14.5 `esp32-c6` (ESP32-C6 RISC-V, 172×320, JD9853)
- **PicoMQTT** замість PubSubClient + підписка на `#` → блоки M8 і M11 тут обов'язкові.
- Ping відсутній (`ESPping` не в `lib_deps`) → блок N6/N7 пропустити; рядка `PING:` на екрані
  не буде.
- **SD увімкнено** (`BOARD_HAS_SD=1`) і перевірено на залізі → блок **F4–F9** виконувати.
  Шина SPI **спільна з дисплеєм** (`SD_SCK=1`/`SD_MOSI=2` = `TFT_SCLK`/`TFT_MOSI`), тому тут
  обов'язковий F8 — саме на цій конфігурації дедлок на `paramLock` вішає плату намертво.
- Якщо картка раптом не монтується (`sdCommand(): Card Failed! cmd: 0x00`) — **не** кидатися
  міняти піни: вони підтверджені документацією Waveshare. Спершу `sdbb`: якщо він дає
  `CMD0 -> 01`, залізо справне і питання в посадці картки в слоті.
- `TFT_BL` не визначений (ні в build_flags, ні в `Setup_JD9853_C6.h`) → команда `brightness`
  зберігає значення, але фізично на підсвітку не впливає (D6b).
- **Єдина плата з IMU** — блок **V** тільки тут. Тач (AXS5106L) та IMU (QMI8658A) сидять на
  спільній I²C-шині (SDA=18/SCL=19), тому будь-яка проблема з шиною б'є по обох одразу: якщо
  «зник» тач, спершу `i2cscan`, і лише потім шукати в драйвері.
- Кнопка **BOOT на GPIO9** (перевірено на залізі; документація Waveshare помилково називає
  GPIO8). `FLIP_BUTTON_PIN` навмисно не заданий — орієнтацію тут перемикає IMU, тож блок **B**
  пропустити.
- RISC-V: саме тут перевіряються формати `%u` (R9) і робота JPEGDEC замість TJpg_Decoder (I1).
- Одноядерний: мережевий таск і `loop()` конкурують за єдине ядро — стежити за loop rate під
  час M11.

### 14.6 `esp32-c6-lcd096` (ESP32-C6, 160×80, ST7735S)
- **Порядок ініціалізації критичний**: SPI-шина спільна з SD, `setupSD()` робить `SPI.begin()`
  і має відпрацювати **до** `setupDisplay()`. Якщо дисплей чорний — перевіряти саме це.
- ⚠️ **Відоме відкрите питання: білі смуги зліва/справа** — залишки заводської прошивки, які
  наш код не перезаписує. Робоча гіпотеза (зафіксована в `include/Setup_ST7735_C6_LCD096.h`):
  offset2 має бути `(1, 26)`, а не `(26, 1)`, бо плата працює з `TFT_ROTATION=1`, а Arduino_GFX
  застосовує offset2 вже до повернутих осей. **Перевірити експериментом:** поміняти offset2
  місцями, перепрошити, подивитись, чи зникли смуги.
- Кнопка на **GPIO9** (не GPIO0, як на решті плат) — B1/B2 перевіряти саме нею.
- Найменший екран: рядок WiFi виводиться в короткому форматі, без відсотків (N2).
- Розділ LittleFS лише 1.5 MB — див. попередження про вміст `data/` у 0.2.
- PicoMQTT → M8 і M11 обов'язкові.

### 14.7 `esp32-c3` (ESP32-C3 SuperMini, RISC-V, **без екрана**)
- **Перша й поки єдина безекранна плата.** `BOARD_HAS_DISPLAY=0` перемикає `src/TftInstance.h`
  на заглушку `include/Setup_Headless.h` — клас з API `TFT_eSPI`, у якого всі методи порожні
  й inline. Тому блоки **D**, **I**, **T**, **V**, **L** пропускати, а не фіксувати як fail.
- Команди `flip`, `clock`, `brightness` **є в `list`** (зареєстровані поза `#if`) і мовчки
  нічого не роблять. У S3 їх наявність перевіряти, ефект — ні. `status sys` друкує
  `Display: 0x0` — це норма, а не збій ініціалізації.
- **Кнопки немає**: `FLIP_BUTTON_PIN` свідомо не заданий, бо вся його логіка в `main.cpp`
  дисплейна (flip, яскравість, показ годинника). B1/B2 не застосовні.
- **LED на GPIO8, інверсна логіка** (LOW = світиться) — єдиний засіб індикації на платі.
  B4 (`blink off`/`blink on`) тут обов'язковий: разом з `esp8266` це єдині два env із
  `BLINK_LED_PIN`.
- **SD немає** (`BOARD_HAS_SD=0`) → з блоку **F** лише LittleFS-тести.
- **Ping немає** (`ESPping` не в `lib_deps`) → N6, N7 пропускати.
- PicoMQTT → **M8 і M11 обов'язкові**, як на обох C6. Дзеркало консолі (M20–M27) теж
  застосовне.
- **EcoFlow увімкнено** (`HAS_ECOFLOW_CLIENT=1`, `ECOFLOW_AUTOCONNECT=1`) — блок **E**
  проходити повністю. Запас heap тут більший, ніж на C6 з дисплеєм: немає ні спрайта,
  ні буфера фону, при 400 КБ SRAM без PSRAM.
- USB-Serial/JTAG (`/dev/ttyACM*`), `monitor_rts = 0` / `monitor_dtr = 0` — відкриття порту
  плату не ресетить, тож `./esp` читає стан, накопичений з моменту старту.
- Розділи: app 2 MB, LittleFS 1.5 MB (`partitions_c3.csv`) — див. попередження про вміст
  `data/` у 0.2.
- Власний `build_src_filter` додає `src-esp32-c3/` — якщо після правки в `src/` поведінка
  на C3 розійшлась з рештою плат, дивитись спершу туди.

### 14.8 `esp8266` (NodeMCU + SSD1306 128×64)
- Монохромний екран (`SPRITE_COLOR_DEPTH=1`): годинник і 2–3 рядки інфо, циклічна зміна екранів
  (`DISPLAY_INFO` / `NETWORK` / `UPTIME`) кожні 3 с — перевірити, що цикл іде.
- `BLINK_LED_PIN=2` (D4) → тест B4. Друга така плата — `esp32-c3` (GPIO8); на решті env
  вбудованого LED не задано.
- `ConfigStorage` працює не через NVS, а через файли `/.nvs/<env>/<key>.<type>` у LittleFS —
  блок **C** перевіряє саме цю гілку. `status cfg` має показувати ті ж ключі, що й на ESP32.
- Ping відсутній; `ESP8266Ping` не в `lib_deps`.
- 80 KB RAM — після `status sys` звіряти вільну купу; поштова бібліотека (ReadyMail) тут особливо ненажерлива.
- Немає SD і touch.
