# Тест-план: приймальна перевірка по пристроях

> Ручний чек-лист для перевірки прошивки на реальному залізі. Автотестів у проєкті немає
> (`test/` порожня), тому це єдиний рівень перевірки понад «зібралось».
>
> Конфігурація кожної плати — таблиця «Матриця фіч» у `docs/architecture.md`. Тут кожен тест
> позначено, на яких environments він застосовний; решту — пропускати, а не «фіксувати як fail».

---

## 0. Підготовка

### 0.1 Передумови

- `secrets.ini` у корені (не в git). Мінімум: `wifi_ssid`, `wifi_password`, `mqtt_host`,
  `mqtt_port`, `mqtt_client_id`, `mqtt_lwt_topic`, `mqtt_topic_prefix`.
  `mqtt_client_id = "mqtt-${PIOENV}"` і `mqtt_lwt_topic = "devices/${PIOENV}/status"` —
  ідентичність плати підставляється автоматично з імені env.
- Брокер MQTT доступний, і є `mosquitto_sub` / `mosquitto_pub` на робочій машині.
- Порт пристрою. У проєкті вже траплялись обидва варіанти: `/dev/ttyUSB0` (USB-UART:
  `esp32-st7789`, `ttgo-t1`, `esp8266`) і `/dev/ttyACM*` (native USB CDC: обидві C6, S3-плати).

### 0.2 Команди

```bash
export ENV=esp32-c6-lcd096          # ім'я environment
export PORT=/dev/ttyACM1            # порт пристрою

# прошивка + монітор
pio run -e $ENV --upload-port $PORT --monitor-port $PORT -t upload -t monitor

# файлова система (LittleFS) - ОКРЕМА команда, не робиться разом з upload
pio run -e $ENV --upload-port $PORT -t uploadfs

# лише монітор
pio device monitor -p $PORT -b 115200
```

`uploadfs` обов'язковий для плат із `LITTLEFS_BACKGROUND_IMAGE` (4848s040, s3-lcd147, c6,
c6-lcd096) і для тесту `dump-asuswrt` (читає `/asus-get_clientlist.json`).

> ⚠️ **`data/` містить не лише асети.** Разом із зображеннями на пристрій заливаються
> `convert` (скомпільований бінарник, 148 KB), `stb_image.h` (276 KB), `convert.c`,
> `convert.py`, `FloatPixel.hpp` — разом ~476 KB, тобто ~40 % розділу LittleFS на платах
> з 1.5 MB spiffs (`esp32-st7789`, `esp32-c6-lcd096`). Перед `uploadfs` варто або тимчасово
> прибрати їх із `data/`, або перенести конвертер у `tools/` назавжди.

### 0.3 Базовий MQTT-моніторинг (тримати відкритим під час усіх мережевих тестів)

```bash
# <prefix> - значення mqtt_topic_prefix; на пристрої його показує команда `dump-mqtt`
mosquitto_sub -h <broker> -p 1883 -t "<prefix>/#" -v \
  -F "@Y-@m-@d @H:@M:@S [q@q/r@r] %-50t %p"
```

| # | Дія | Очікуваний результат |

## 5. M — MQTT

Актуальний префікс і стан з'єднання показує `dump-mqtt`. Нижче `<prefix>` = `mqtt_topic_prefix`,
`<env>` = ім'я environment.

| # | Дія | Очікуваний результат | Плати |
| :-- | :--- | :--- | :--- |
| M1 | `dump-mqtt` | `isConnected = yes, topic prefix = '<prefix>'` | усі |
| M2 | Дивитись `mosquitto_sub -t "<prefix>/#"` під час старту пристрою | Приходить retained-повідомлення в `<prefix>/devices/<env>/status` з online-текстом | усі |
| M3 | `publish test/hello world` | У підписнику з'являється `<prefix>/test/hello world`, у консолі `publish (test/hello:world) success` | усі |
| M4 | `mosquitto_pub -t "<prefix>/command/mqtt-<env>" -m "clock off"` | На пристрої: `command clock off`, годинник зникає | усі |
| M5 | Те саме з `-m "status sys"` | Пристрій друкує в Serial повний дамп системної інфо | усі |
| M6 | Дочекатись 5 хв | У `<prefix>/devices/<env>/status` приходить `hearbeat` *(так, у коді саме з такою орфографією)* | усі |
| M7 | Смикнути живлення пристрою (не `reboot`) | Брокер публікує LWT-offline у `<prefix>/devices/<env>/status` | усі |
| M8 | `reboot` через консоль | LWT-offline із текстом **`reboot`** доходить до брокера **до** перезавантаження *(регресія R12 — до фіксу на PicoMQTT-платах не доходив ніколи)* | усі; критично для **c6**, **c6-lcd096** |
| M9 | `mqtt-prefix` | Показує поточний префікс | усі |
| M10 | `mqtt-prefix testpfx` → `reboot` → `dump-mqtt` | Після ребуту префікс `testpfx`, топіки в підписнику змінили корінь. **Повернути назад** тим самим шляхом | усі |
| M11 | Флуд: `for i in $(seq 1 300); do mosquitto_pub -t "<prefix>/devices/x/status" -m "$i"; done` одночасно з важкою командою на пристрої (`status sd+` або `blur 8 3`) | Пристрій живий; у консолі допускається `[MQTT] черга переповнена, відкинуто: N вхідних, M вихідних`; **не** має бути OOM/reset *(регресія R11)* | усі; критично для **c6**, **c6-lcd096** (підписка на `#`) |

## 7. F — Файлові системи

| # | Дія | Очікуваний результат | Плати |
| :-- | :--- | :--- | :--- |
| F1 | `status littlefs` | Перелік файлів із розмірами + підсумок `Used / Total / Free` | усі |
| F2 | `status flash` | Таблиця розділів: `nvs`, `app`, `coredump`, `spiffs`; рядки **цілі, без обрізань і без сміття** *(регресія R1)* | усі |
| F3 | `status flash+` | Те саме + рядки `sha256:` для app-розділу | усі |
| F4 | `status sd` | MBR-таблиця розділів. На «superfloppy»-картках (FAT без MBR) — рядок `MBR not found`, це не помилка | 4848s040, s3-lcd147, st7789, **c6**, c6-lcd096 |
| F5 | `status sd+` | Тип картки, лістинг кореня (до 49 записів), розмір/used/free у відсотках | ті самі |
| F6 | Вийняти SD і виконати `status sd`, потім `status sd+` | `SD не змонтована - читати нічого`, **без** зависання чи reset *(регресія R15 — до фіксу `status sd` без картки гарантовано перезавантажував плату: `readRAW()` не перевіряє `_pdrv` і читає `s_cards[0xFF]` за межами масиву)* | ті самі |
| F7 | `dump-asuswrt` | Читає `/asus-get_clientlist.json` з LittleFS і друкує `client.name=…`. Потребує попереднього `uploadfs` | усі |
| F8 | `status sd` і `status sd+` на платах зі спільною шиною | Команда відпрацьовує до кінця. **Зависання намертво = регресія R16** (`YIELD_DISPLAY_BUS()` не віддав шину дисплея, дедлок на не рекурсивному `SPIClass::paramLock`) | **c6**, c6-lcd096 |
| F9 | `sdbb` на змонтованій картці, далі `reboot` | Дамп `CS=HIGH` — суцільні `FF`; `CMD0 відповідь` містить `01`; усі три лінії `керується: ТАК`. Висновок чесно каже, що проба нічого не діагностує, бо картка вже була змонтована. Після проби картка демонтована — це очікувано, повертається після `reboot` | c6, c6-lcd096 |

## 8. I — Фон і ефекти зображення

Команди ефектів компілюються лише за наявності `LITTLEFS_BACKGROUND_IMAGE` → доступні на
**4848s040, s3-lcd147, c6, c6-lcd096**. На `esp32-st7789` фон вбудований у прошивку
(`BACKGROUND_IMAGES_COUNT=1`), команд ефектів там немає. На `ttgo-t1` і `esp8266` фону немає взагалі.

| # | Дія | Очікуваний результат | Плати |
| :-- | :--- | :--- | :--- |
| I1 | Після `uploadfs` + старту глянути консоль | `jpeg` -логер: `"<шлях>" <W>x<H> (<байт>) - free (<купа>)` і далі `Loaded WxH, depth: 16 біт, buffer: … B, memory: RAM\|PSRAM`. Фон видно на екрані | 4 плати |
| I2 | `blur 2 1` | `blur applied: radius=2 passes=1`, фон помітно розмитий | 4 плати |
| I3 | `blur 8 3` на 480×480 | Спрацює, але **надовго заблокує loop()** (мільйони float-операцій без yield). Перевірити, що не спрацьовує task watchdog і MQTT не відвалюється | 4848s040 |
| I4 | `tint FF8800 0.5`, `sepia 1.0`, `invert`, `thermal`, `vignette 0.5`, `pixelate 8` | Кожна друкує `… applied: …` і візуально змінює фон | 4 плати |
| I5 | `blur 0` / `blur 99` | `radius must be 1-8`, фон не змінюється | 4 плати |
| I6 | `tint XYZ` | `color must be 6 hex chars, e.g. FF8800` | 4 плати |
| I7 | `background /background-03-320x172.jpg` | Фон змінюється на вказаний; неіснуючий шлях → `File not found: …`, попередній фон лишається | s3-lcd147, c6 |
| I8 | Після серії з 10+ ефектів — `status sys` | Вільна купа не деградує від виклику до виклику (ефекти працюють in-place) | 4 плати |

## 12. R — Регресії після код-рев'ю

| # | Що виправлено | Як перевірити | Де критично |
| :-- | :--- | :--- | :--- |
| R1 | `ILogger`: не термінований буфер + текст як format-рядок | F2, F3, F5 | усі |
| R2 | `EventDispatcher::dispatch()` повертав dangling reference | S7 (`reboot` проходить штатно) | усі |
| R3 | `String` у varargs `%s` (UB) | S5, N5 | усі |
| R4 | `Free PSRAM`: 2 специфікатори на 1 аргумент | S4 — рядки `Total PSRAM` і `Free PSRAM` обидва з коректними числами | **4848s040, s3-lcd147** |
| R5 | `TaskController::loop()` — інвалідація ітераторів | T7; на платах без touch — S2 (довгий аптайм) | 4848s040, st7789 |
| R9 | `%d` для `uint32_t` на RISC-V | D2, D3 | **c6, c6-lcd096** (RISC-V), решта — регрес-контроль |
| R11 | Необмежені черги MQTT | M11 | **c6, c6-lcd096** |
| R12 | LWT перед ребутом не встигав піти | M8 | **c6, c6-lcd096** |
| R13 | Запис NVS на кожну зміну авто-яскравості | C4 | **st7789** |
| R14 | `sprintf`→`snprintf`, стартовий `minPing=9999`, пінг без WiFi | N6, N7 | 4 плати з ping |
| R15 | `status sd` без картки → reset (`readRAW()` віддає `_pdrv=0xFF` у `s_cards[]` без перевірки меж) | F6 | **усі з SD** |
| R16 | Дедлок на `SPIClass::paramLock`: доступ до SD з-під відкритої транзакції дисплея | F8 | **c6, c6-lcd096** |

### Виправлення, які в поточній конфігурації перевірити НЕ можна

Чесно фіксую, щоб ці пункти не імітували в протоколі:

| Виправлення | Чому недосяжне | Що зробити, якщо треба перевірити |
| :--- | :--- | :--- |
| `ScreenLogTail`: читання за `'\0'` при `+ skip` | `SCREEN_LOG_TAIL_LINES=0` у **всіх** 7 env — блок не компілюється | Тимчасово поставити `-D SCREEN_LOG_TAIL_LINES=20` для `ttgo-t1`/`st7789`/`s3-lcd147`, викликати `status sys` і подивитись на хвіст логу на екрані |

## 13. Особливості й ризики по платах

### 13.1 `esp32-4848s040` (ESP32-S3, 480×480, RGB-панель)
- Єдина плата з `DISPLAY_SPLIT_COUNT=1` при 480×480 — спрайт на весь кадр це 460 KB, живе
  **тільки** завдяки OPI PSRAM. У `status sys` перевірити `PSRAM found: YES`, інакше дисплей
  не ініціалізується.
- Touch GT911 — повний блок **T**.
- Найважчі ефекти (I3): 480×480 × radius 8 × 3 passes. Це найкращий стрес-тест на watchdog.
- Кнопки немає (`FLIP_BUTTON_PIN` не заданий) — блок **B** пропустити, крім B3.

### 13.2 `esp32-s3-lcd147` (ESP32-S3, 172×320)
- SD через **SD_MMC 4-bit**, не SPI. `status sd` іде через `SDCardInspector::printAll(SD_MMC, …)`.
  Якщо картка не визначається — перевіряти саме `SD_MMC.setPins()` у `setupSD()`, а не SPI-піни.
- `TOUCH_CS=0` у build_flags — це заглушка проти warning'а TFT_eSPI, touch немає.

### 13.3 `esp32-st7789` (ESP32, 240×320)
- **Єдина плата з light sensor** — блок **L** тільки тут, і саме тут перевіряється C4 (NVS wear).
- **Єдина плата з вбудованим фоном** (`BACKGROUND_IMAGES_COUNT=1`): фон із PROGMEM, команд
  ефектів немає. Блок **I** — лише перевірити, що фон видно.
- `DISPLAY_SPLIT_COUNT=6` — найдрібніше розбиття, найкращий кандидат на перевірку D7.
- SD на **400 kHz** (`SD_FREQ=400000`) — лістинг великої картки буде помітно повільним, це не баг.
- Gmail і `ESP Mail Client` тут не підключені.

### 13.4 `ttgo-t1` (ESP32, LilyGO T-Display 135×240)
- Найпростіша конфігурація: без SD, touch, сенсора, фону. Фактично перевіряє «спільне ядро»:
  дисплей + WiFi + NTP + MQTT + консоль.
- `BACKGROUND_IMAGES_COUNT=0` і без `LITTLEFS_BACKGROUND_IMAGE` → `drawBackgroundImage()`
  щокадру робить `display.clear()`. Якщо помітне мерехтіння — це очікувана поведінка цієї
  конфігурації, а не регресія.
- `upload_speed = 115200` (навмисно) — прошивка помітно довша.

### 13.5 `esp32-c6` (ESP32-C6 RISC-V, 172×320, JD9853)
- **PicoMQTT** замість PubSubClient + підписка на `#` → блоки M8 і M11 тут обов'язкові.
- Ping відсутній (`ESPping` не в `lib_deps`) → блок N6/N7 пропустити; рядка `PING:` на екрані
  не буде.
- **SD увімкнено** (`BOARD_HAS_SD=1`) і перевірено на залізі → блок **F4–F9** виконувати.
  Шина SPI **спільна з дисплеєм** (`SD_SCK=1`/`SD_MOSI=2` = `TFT_SCLK`/`TFT_MOSI`), тому тут
  обов'язковий F8 — саме на цій конфігурації дедлок на `paramLock` вішає плату намертво.
- Якщо картка раптом не монтується (`sdCommand(): Card Failed! cmd: 0x00`) — **не** кидатися
  міняти піни: вони підтверджені документацією Waveshare. Спершу `sdbb`: якщо він дає
  `CMD0 -> 01`, залізо справне і питання в посадці картки в слоті.
- `TFT_BL` не визначений (ні в build_flags, ні в `Setup_JD9853_C6.h`) → команда `brightness`
  зберігає значення, але фізично на підсвітку не впливає (D6b).
- RISC-V: саме тут перевіряються формати `%u` (R9) і робота JPEGDEC замість TJpg_Decoder (I1).
- Одноядерний: мережевий таск і `loop()` конкурують за єдине ядро — стежити за loop rate під
  час M11.

### 13.6 `esp32-c6-lcd096` (ESP32-C6, 160×80, ST7735S)
- **Порядок ініціалізації критичний**: SPI-шина спільна з SD, `setupSD()` робить `SPI.begin()`
  і має відпрацювати **до** `setupDisplay()`. Якщо дисплей чорний — перевіряти саме це.
- ⚠️ **Відоме відкрите питання: білі смуги зліва/справа** — залишки заводської прошивки, які
  наш код не перезаписує. Робоча гіпотеза (зафіксована в `include/Setup_ST7735_C6_LCD096.h`):
  offset2 має бути `(1, 26)`, а не `(26, 1)`, бо плата працює з `TFT_ROTATION=1`, а Arduino_GFX
  застосовує offset2 вже до повернутих осей. **Перевірити експериментом:** поміняти offset2
  місцями, перепрошити, подивитись, чи зникли смуги.
- Кнопка на **GPIO9** (не GPIO0, як на решті плат) — B1/B2 перевіряти саме нею.
- Найменший екран: рядок WiFi виводиться в короткому форматі, без відсотків (N2).
- Розділ LittleFS лише 1.5 MB — див. попередження про вміст `data/` у 0.2.
- PicoMQTT → M8 і M11 обов'язкові.

### 13.7 `esp8266` (NodeMCU + SSD1306 128×64)
- Монохромний екран (`SPRITE_COLOR_DEPTH=1`): годинник і 2–3 рядки інфо, циклічна зміна екранів
  (`DISPLAY_INFO` / `NETWORK` / `UPTIME`) кожні 3 с — перевірити, що цикл іде.
- **Єдина плата з `BLINK_LED_PIN`** → тест B4 тільки тут.
- `ConfigStorage` працює не через NVS, а через файли `/.nvs/<env>/<key>.<type>` у LittleFS —
  блок **C** перевіряє саме цю гілку. `status cfg` має показувати ті ж ключі, що й на ESP32.
- Ping відсутній; `ESP8266Ping` не в `lib_deps`.
- 80 KB RAM — після `status sys` звіряти вільну купу; ESP Mail Client тут особливо ненажерливий.
- Немає SD і touch.
