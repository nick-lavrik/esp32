# Інтеграція з EcoFlow

Читання телеметрії павербанків EcoFlow (заряд, наявність мережі, потужності) через MQTT
хмари EcoFlow. Код — `src/Ecoflow/`, вмикається build-флагом `HAS_ECOFLOW_CLIENT=1`
(наразі `esp32-c6` і `esp32-c6-lcd096`).

> Усі факти нижче отримані експериментально на живому акаунті — офіційна документація
> EcoFlow або мовчить про них, або суперечить дійсності. Числа в прикладах справжні.

## Два канали, і чому потрібні обидва

| | Open Platform | Приватний API застосунку |
| :--- | :--- | :--- |
| хост | `api-e.ecoflow.com` | `api.ecoflow.com` |
| auth | `accessKey` + `secretKey` | `email` + `password` |
| префікс акаунта | `open-…` | `app-…` |
| топік | `/open/{account}/{sn}/quota` (+`/status`) | `/app/device/property/{sn}` |
| офіційність | документований | неофіційний, може змінитись без попередження |
| набір полів | **обрізаний для частини моделей** | повний, як у застосунку |

Приклад різниці на DELTA mini: Open Platform дає **23 поля**, де всі ватти жорстко нулі
(єдине поле про вхід — `bmsMaster.inputWatts`, і воно завжди `0`, попри реальні 45 Вт).
Той самий пристрій у приватному каналі віддає **201 поле**, зокрема `inv.acInVol=211658`,
`inv.acInFreq=50`, `inv.inputWatts=45`.

**Права не перетинаються:** app-креденшели на `/open/…` → `denied`, і навпаки. Тому
одночасно тримати обидва канали немає сенсу — це два TLS-з'єднання по ~57 КБ heap.

### Вибір каналу — за префіксом акаунта

`EcoflowClient::channelFromAccount()`: `app-…` → приватний канал, будь-що інше → Open
Platform. Тобто в `secrets.ini` достатньо підмінити `ecoflow_mqtt_username`/`password` —
код сам обере схему топіків, clientId і формат парсингу. Open Platform лишається робочим
fallback, якщо приватний API колись зламається.

### clientId для приватного каналу

Обов'язково `ANDROID_<будь-що>_<userId>`. Перевірено межі:

| clientId | результат |
| :--- | :--- |
| `ANDROID_test_<свій userId>` | ✅ дані йдуть |
| `<свій userId>` | ❌ `Connection Refused: not authorised` |
| `ANDROID_<uuid>_<чужий userId>` | ❌ not authorised |
| `IOS_test_<свій userId>` | ❌ not authorised |

Саме тому в `secrets.ini` потрібен `ecoflow_user_id` — він приходить із логіну
(`data.user.userId`).

## Автентифікація

### Open Platform

`GET /iot-open/sign/certification` з заголовками `accessKey`/`nonce`/`timestamp`/`sign`.
Креденшели стабільні між викликами, тому зберігаються в `secrets.ini`.

### Приватний API

1. `POST /auth/login` — `{email, password: base64(pass), scene:"IOT_APP",
   userType:"ECOFLOW", os:"android"}` → JWT (**exp = рівно 30 днів**) + `data.user.userId`
2. `GET /iot-auth/app/certification`, заголовки `lang: en_US`,
   `authorization: Bearer <JWT>` → `certificateAccount` (`app-…`), `certificatePassword`

**MQTT-креденшели стабільні між викликами** — перевірено двома логінами поспіль. JWT
потрібен лише щоб їх отримати, тому 30-денний TTL на постійну роботу не впливає:
випустив раз (`ecoflow-app-login`), поклав у `secrets.ini` — і все.

> `port` тут приходить **рядком** (`"8883"`), на відміну від Open Platform, де це число.

### Формула підпису — різна для GET і POST

Це коштувало кількох годин, тож фіксується явно:

- **GET**: canonical = `accessKey=…&nonce=…&timestamp=…`. Query-параметри (`?sn=…`)
  у підпис **не входять**.
- **POST**: canonical = **flatten тіла** + ті самі три поля, відсортовані за ASCII:
  `params.quotas[0]=inv.inputWatts&params.quotas[1]=…&sn=…&accessKey=…&nonce=…&timestamp=…`

Діагностична ознака, що підпис зійшовся: код відповіді перестає бути `8521
signature is wrong` і стає змістовним (`1006`, `8524 invalid parameter`). Порожній масив
у flatten не дає елементів — на цьому й вдалося зачепитися.

`EcoflowSigner::sign(extraParams)` реалізує GET-схему. Для POST потрібен flatten —
у коді поки не реалізовано (знадобиться для команд керування `/set`).

## ACL: тільки точні топіки

Брокер відхиляє **будь-який** wildcard: `/open/{account}/#`, `/open/{account}/+/quota`
і навіть `/open/{account}/{sn}/#`. Приймає лише точні. Тому:

- серійні номери потрібні **до** першої підписки → вони прошиті в
  `EcoflowDeviceRegistry` (`kDevices`), а не тягнуться з REST;
- підписка — окрема на кожен `{sn}`.

Дозволені підтопіки Open Platform: `quota`, `status`, `set`, `set_reply`.
Заборонені: `get`, `get_reply`.

> Wildcard лишається в `MqttConfig::rootSubscribeTopic`, і це безпечно: PicoMQTT реєструє
> його через `SubscribedMessageListener` — тобто **локально**, як фільтр-диспетчер вхідних
> повідомлень. Брокеру він не надсилається. Плутанина між цими двома рівнями — головна
> пастка тут.

## quota — це дельта, а не знімок

Пристрій шле **лише те, що змінилось**. За 90 секунд DELTA mini надіслала 23 поля,
DELTA Pro — 242. Наслідки, які визначили весь дизайн:

**1. Стан накопичується.** `EcoflowDeviceState` має третій стан «невідомо»
(`socPercent = -1`, `grid = Unknown`) — плутати його з «мережі немає» не можна.

**2. Пріоритет полів застосовується до НАКОПИЧЕНОГО стану, не до повідомлення.**
На цьому я обпікся двічі. Приклад: DELTA 2 з extra battery шле
`bms_emsStatus.lcdShowSoc=72` (системний заряд) і `bms_bmsStatus.soc=61` (лише основна
батарея) **різними** повідомленнями. Логіка «перший наявний зі списку пріоритетів
у цьому повідомленні» давала 61 % замість 72 %. Тому `kSocPriority` шукає в
`trackedParams`, а не в `params`.

**3. Після старту частина стану невідома** — доки поле реально не зміниться. Лікується
REST-знімком (нижче).

## REST-знімок: `GET /iot-open/sign/device/quota/all?sn=…`

Повертає **повний** стан (242–353 поля), зокрема `inv.acInVol`. Викликається один раз
після появи NTP-часу (підпис містить `timestamp`) і командою `ecoflow-sync`.

Один `suspend()` MQTT на всі пристрої, а не на кожен: розрив і підняття TLS коштують
~57 КБ heap і кілька секунд.

**Доступний не для всіх:** DELTA mini і Smart Generator віддають
`1006 current device is not allowed to get device info` — і в GET, і в POST з правильним
підписом, і на `api-e`, і на `api`. Тобто це властивість **моделі**, не регіону й не
формули. `EcoflowDeviceState::snapshotAvailable=false` не дає смикати такий пристрій
повторно.

## Реєстр пристроїв

`src/Ecoflow/EcoflowDeviceRegistry.{hpp,cpp}` — прошитий перелік + накопичений стан.

### Нормалізація ключів

API мішає схеми навіть для одного пристрою: DELTA 2 у MQTT шле `acInVol`, а в
REST-знімку те саме поле зветься `inv.acInVol`. Тому всі ключі зводяться до одного
вигляду (`normalizeKey`): `camelCase` → `snake_case`, `.` → `_`.

```
inv.acInVol   → inv_ac_in_vol
bmsMaster.soc → bms_master_soc
```

Дві деталі: роздільник вставляється лише там, де перед великою літерою йде маленька або
цифра (інакше `iconACState` → `icon_a_c_state`), і роздільники не дублюються (в API вже
є `bms_bmsStatus.inputWatts`).

### Що зберігається

- **білий список** (`kWhitelistParams`) — завжди: `*soc`, `*ac_in_vol`, `*ac_in_freq`,
  `*input_watts`, `*remain_time`, `*temp` тощо;
- **чорний список** (`kBlacklistParams`) — ніколи, навіть при `capture all`:
  `pd_icon*` (стан іконок на екрані станції — десятки полів, що міняються постійно);
- **решта** — лише при `ecoflow-capture on` (для DELTA 2 це 101 поле проти 64).

Стеля `kMaxTrackedParams = 400` на пристрій, з лічильником `droppedParams` — щоб
обрізання не виглядало як «пристрій цього не шле».

### Заряд: EMS проти BMS

З extra battery різниця принципова:

```
bms_bmsStatus.soc        = 61   ← основна батарея
bms_slave.soc            = 82   ← extra battery
bms_emsStatus.lcdShowSoc = 72   ← СИСТЕМНИЙ, його показує застосунок і екран станції
```

`kSocPriority` ставить EMS-рівень (`lcdShowSoc`) вище за BMS — це заряд усієї системи.

### Час до заряду / розряду

EcoFlow віддає **одне** поле `remainTime` і на заряд, і на розряд — окремих немає. Сенс
видно з сусідньої колонки `GRID`. З extra battery кожна батарея має власний прогноз
(`pd.remainTime=336`, `bms_slave.remainTime=130`), тому береться **максимум**: система
готова, коли закінчить остання.

`kRemainTimeUnknownFrom = 5900` — усе, що більше, EcoFlow віддає як «невизначено»
(траплялись 5999, 5940, 5939 ≈ 99 годин). `0` теж означає «нема що прогнозувати».

### Наявність мережі (on-grid)

Пріоритет: `acInVol` → `acInFreq` → висновок із динаміки заряду.

Чому не за потужністю: `inputWatts` падає до нуля, коли батарея зарядилась, хоча мережа
на місці — виходили б фантомні «зникнення світла».

Для пристроїв, які не шлють ні напруги, ні частоти (DELTA mini в Open Platform), стан
виводиться з **динаміки SOC** і позначається зірочкою (`on-grid*`, прапорець
`gridInferred`) — щоб не видавати здогад за вимір. Обмеження: при 100 % заряду SOC
перестає рости і стан «замерзає». У приватному каналі ця проблема зникає — там є
справжній `acInVol`.

### Присутність: три стани

`online` / `offline` / `unknown`. Останній — коли жодного MQTT-повідомлення ще не чули
(`lastMessageMs == 0`). Потрібен тому, що REST-знімок заповнює заряд і час, але **не
доводить**, що пристрій живий: раніше це виглядало як «offline зі свіжими даними».

`expireStale()` позначає offline після 5 хвилин тиші — у приватному каналі окремого
`/status` немає, тож присутність визначається саме тишею.

## Команди

| Команда | Що робить |
| :--- | :--- |
| `ecoflow` | таблиця: `# SERIAL NAME PRESENCE CHARGE GRID TIME SPAN` |
| `ecoflow-params [sn\|index] [pattern]` | захоплені параметри; patttern — glob по нормалізованому ключу (`*_in_*`) |
| `ecoflow-capture <on\|off> [sn\|index\|all]` | захоплення ВСІХ полів, не лише білого списку |
| `ecoflow-sync` | REST-знімок повного стану для всіх пристроїв |
| `ecoflow-devices` | список пристроїв із хмари (звірка з прошитим переліком) |
| `ecoflow-app-login` | випуск app-креденшелів (email+password → account/password/userId) |
| `ecoflow-cert` | перевипуск Open Platform креденшелів |
| `ecoflow-start` / `ecoflow-stop` | підняти / прибрати MQTT-сесію (звільняє ~57 КБ) |
| `ecoflow-auto [on\|off]` | підключатись на старті (NVS, діє з наступного boot) |
| `ecoflow-verbose [on\|off]` | дамп телеметрії в лог |

Пристрій задається індексом зі списку або серійником. Запит нормалізується, тому
`ecoflow-param 1 inv.acInVol` знаходить `inv_ac_in_vol`.

## Пам'ять

TLS-сесія — найдорожче: `ecoflow-stop` звільняє ~57 КБ (перевірено: 106 КБ → 164 КБ
вільних). Тому:

- `ECOFLOW_AUTOCONNECT=0` дозволяє не піднімати її на старті;
- REST-виклики роблять `MqttClient::suspend()` — дві одночасні TLS-сесії ESP32-C6 не
  тягне, mbedTLS падає з `BIGNUM - Memory allocation failed` ще на RSA-операції.

Стеки TLS-тасків — 16 КБ. Спроба зрізати до 10 КБ «за виміром» (`headroom` показував
запас 12 КБ) закінчилась **зависанням плати без panic-логу**: замір покривав лише
стабільну сесію, а в лозі є рідший глибший шлях `DNS Failed → Connect fail → повторний
хендшейк`. Не повторювати.

## Як змусити DELTA 2 штовхати дані часто?
Щоб активувати швидке надсилання даних без відкритого застосунку, вам потрібно імітувати 
поведінку офіційного клієнта за допомогою публікацій у топіки керування (/set або /get).

### Крок 1: Запит на миттєве оновлення (запуск потоку)

Одразу після підключення до MQTT-брокера відправте в топік `/app/device/property/{sn}` 
(або в аналогічний структурований топік для запитів, наприклад 
`/app/{user_id}/{sn}/thing/property/get`, залежно від типу вашої авторизації) 
JSON-команду для отримання актуальних даних:

```json
{
    "id": 123456789,
    "version": "1.0",
    "cmdFunc": 254,
    "cmdId": 1,
    "params": {
       "operateType": "latestQuotas"
    }
}
```
Це змусить пристрій вивантажити повний пакет актуальних параметрів у ваш топік очікування.
https://github.com/berezhinskiy/ecoflow_exporter/issues/70


### Крок 2: Підтримка активної сесії (Keep-Alive)
Щоб пристрій знову не заснув через 5 хвилин, налаштуйте таймер у своєму коді, який 
кожні 20–30 секунд відправлятиме порожній пінг або сервісну команду підтримки зв'язку в 
топік керування пристроєм (`.../property/set` або через аналогічний сервісний командний шлях). 
Наприклад, застосунок часто шле команду синхронізації часу `setRtcTime` або `getAllTaskCfg`.
https://github.com/berezhinskiy/ecoflow_exporter/issues/70

## Що лишилось нез'ясованим

- Команди керування (`/set`) не реалізовані — потрібен POST-підпис із flatten тіла.
- DELTA mini і Smart Generator недоступні для REST-читання (`1006`); чи можна це
  увімкнути на developer-порталі — не перевірено.
- Семантика `remainTime` при розряді з extra battery (максимум чи сума) перевірялась
  лише на заряді.
