# ML на ESP32: план

Мета — пройти повний цикл «дані → модель на ПК → інференс на платі» на тому
залізі, що вже є, без докупівлі датчиків. Документ — план і запис рішень;
невиконане по ходу робіт іде в `docs/tech_debt.md`, стабільні знахідки «як
працює» — у «Карту коду» `docs/architecture.md`.

Статус на 2026-10-03: **план, нічого не реалізовано.**

## 0. Вихідні дані

### Залізо

| Плата | Чип | PSRAM | Що корисне для ML |
| :--- | :--- | :---: | :--- |
| `esp32-c6` | RISC-V 160 МГц, 1 ядро | — | IMU QMI8658A (I²C `0x6B`, спільна шина з тачем AXS5106L), тач, SD (SPI спільна з дисплеєм) |
| `esp32-4848s040` | ESP32-S3, 2 ядра, SIMD | 8 МБ | тач GT911 480×480, SD, app-розділ 4 МБ |
| `esp32-s3-lcd147` | ESP32-S3 | 8 МБ | SD_MMC, кнопка — кандидат на CSI-сенсор і майбутній мікрофон |
| `esp32-st7789` | ESP32 | — | фоторезистор на GPIO34 (`LIGHT_SENSOR_PIN`, ADC1 — працює разом з Wi-Fi), тач XPT2046, SD |
| `esp32-c3`, `esp32-c6-lcd096`, `ttgo-t1` | — | — | лише Wi-Fi (CSI) |

Мікрофона й камери немає ніде — голос і зір поза планом (розділ 7).

### Що вже є в коді

- **IMU** (`src-esp32-c6/Qmi8658.{h,cpp}`, `ImuController.cpp`): увімкнений
  лише акселерометр, ±4g, ODR 250 Гц (`CTRL2=0x13`), гіроскоп вимкнений
  (`CTRL3=0x00`, `CTRL7=0x01`). `ImuController::update()` опитує раз на
  100 мс з `loop()` — для жестів замало і нерівномірно.
- **Тач** (`lib/TouchScreen/TouchEvents`): події `onTouch`/`onRelease`/
  `onClick`/`onSwipe*`/`onHold`. Потоку точок під час руху (траєкторії)
  **немає** — його доведеться додати для рукопису.
- **TFLite Micro + ESP-NN — уже у фреймворку.** У
  `framework-arduinoespressif32-libs/<chip>/` для esp32, c3, c6 і s3 лежать
  `include/espressif__esp-tflite-micro` і `lib/libespressif__esp-tflite-micro.a`
  (і `esp-nn` з оптимізованими ядрами; SIMD-прискорення реально є лише на S3
  і класичному ESP32). Тобто `lib_deps` не потрібен. ⚠ Що заголовки й
  лінкування доступні з PlatformIO-проєкту без додаткових `-I` — **не
  звірено**, це перший крок розділу 2.
- **Wi-Fi CSI увімкнений** у прекомпільованому sdkconfig усіх наших чипів
  (`CONFIG_ESP_WIFI_CSI_ENABLED=y`) — `esp_wifi_set_csi_rx_cb()` доступний з
  Arduino без перезбірки IDF.

### Спільні правила для всіх варіантів

Нічого нового — те, що вже є в `CLAUDE.md`, застосоване до ML:

- **Лог англійською, рівною табличкою**: один тег на повторюваний рядок
  (`[ml-imu]`, `[ink]`, `[csi]`), фіксована ширина полів. Приклад для жесту:
  `[I][ml-imu ] gesture=circle     conf=0.94  ms=  1   win= 142`.
- **Видимість на порталі обов'язкова**: модель, яка тихо перестала
  спрацьовувати, нічим не відрізняється від відсутньої. Кожен варіант має
  картку чи рядок з лічильниками (розпізнано / відкинуто / остання подія).
- **Нові MQTT-топіки — у `docs/mqtt-topics.md` в тому самому коміті.**
- **Fixed-size буфери, без heap у гарячому шляху** — вікна семплів, штрихи,
  кільце CSI мають відомий на етапі компіляції розмір.
- **Без «на виріст»**: спільний ML-шар (`lib/Ml…`) не будуємо, поки не
  з'явиться другий користувач. Варіант 1 живе сам по собі; що з нього
  перевикористати — вирішуємо на варіанті 2, маючи дві реальні реалізації.
- **Дані й скрипти**: скрипти навчання — `tools/ml/` (у git), датасети й
  проміжні артефакти — `.cache/ml/` (поза git). Згенеровані ваги — `.h` у
  git поряд з кодом, що їх використовує, із шапкою «згенеровано
  `tools/ml/xxx.py`, не редагувати руками» і хешем датасету.
- **Кожен небезпечний крок ініціалізації — через `withTrace()`**, щоб ціна
  моделі в heap була видна в `[D][trace]` одразу.

## 1. Жести на `esp32-c6` (IMU)

**Що робить:** плату в руці рухають певним чином (коло, «галочка», мах
вліво/вправо, поворот кистю, подвійний стук), плата впізнає жест і виконує
прив'язану до нього команду.

**Чому першим:** датчик уже є, дані збираються за хвилини, модель мала
(кілька КБ), а сам цикл «зібрав → навчив → прошив» потім повторюється в
усіх інших варіантах.

### 1.0 Каталог жестів

Жести різні за природою, і не всі потребують моделі. Правило: що
описується одним порогом — робиться порогом; модель — лише там, де форму
руху порогом не описати.

| Група | Жест | Як розпізнається | Приклад дії |
| :--- | :--- | :--- | :--- |
| **A. Події без ML** | подвійний стук по корпусу | пік акселерометра ×2 за ≤ 400 мс; ⚠ у QMI8658 є апаратний tap-детектор — звірити з даташитом, може бути безкоштовно | `flip` |
| | струс (shake) | енергія гіроскопа > поріг довше 300 мс | скинути екран на годинник |
| | підняли / поклали | перехід «нерухомо → рух» і навпаки (апаратний motion/no-motion QMI8658 — ⚠ звірити) | розбудити / пригасити підсвітку |
| | екраном донизу | `Z ≈ -1g` стабільно 1 с | «тихий режим» |
| **B. Форма руху — ML** | мах вліво / вправо / вгору / вниз (flick) | MLP | попередній / наступний екран |
| | коло за / проти годинникової | MLP | `dino` / вихід з режиму |
| | поворот кистю вліво / вправо (twist) | MLP; конфлікт з автофліпом — 1.5 | гучніше/тихіше, яскравість |
| | «галочка» V, «Z» у повітрі | MLP або 1D CNN | підтвердити / скасувати |
| **C. Безперервні** | нахил і утримання (tilt) | кут з акселерометра, без класифікації | прокрутка списку, курсор |
| **D. Далека мета** | цифри «в повітрі» (air writing) | 1D CNN, TFLM | ввід числа без тача |

Порядок: **A** (зразу, без датасету — дає корисний результат і перевіряє
FIFO та сегментацію) → **B** перші 4 класи (мах ×4) + `idle` → решта **B**
→ **C** → **D**, якщо цикл B виявиться легким.

### 1.1 Драйвер: гіроскоп і рівномірний потік семплів

- `Qmi8658`: увімкнути гіроскоп (`CTRL3`: ±512 dps, ODR ~112–235 Гц;
  `CTRL7 = 0x03`). Читати акселерометр і гіроскоп одним блоком 12 байт з
  `0x35` (AX..AZ, далі GX..GZ поспіль) — новий метод `readMotion(Sample&)`,
  `readAccel()` лишається для автофліпу.
- **Рівномірність — через FIFO чипа, а не через окремий таск.** `loop()`
  нерівномірний (кадр дисплея — десятки мс), а окремий таск з I²C конкурував
  би з тачем на спільній шині. FIFO QMI8658 накопичує семпли на точній
  частоті ODR, а `loop()` раз на ~50–100 мс забирає пачку. Частота
  дискретизації тоді задається чипом, а не тим, як швидко крутиться `loop()`.
  ⚠ Розмір FIFO, режим і регістри (`FIFO_CTRL`, `FIFO_SMPL_CNT`,
  `FIFO_DATA`) — звірити з даташитом (`docs/datasheet.md`) перед кодом.
- Fallback, якщо FIFO не піде: опитувати в `loop()` з міткою часу на семпл
  і ресемплити на ПК / в інференсі. Гірше, але працює.
- Робоча частота для моделі — **100 Гц**, вікно — до 2 с (200 семплів ×
  6 осей × `int16` = 2.4 КБ RAM).
- Струм: гіроскоп їсть помітно більше за акселерометр. Вмикати його лише
  коли жести увімкнені (`gesture on|off`, ключ у `ConfigStorage`).

### 1.2 Збір датасету

- Serial-команда `gesture record <label> [count]`: показує на екрані
  «3-2-1 → рухайте», пише одне вікно в `/ml/imu/<label>/<NNN>.csv` на SD
  (заголовок `t_ms,ax,ay,az,gx,gy,gz`), повторює `count` разів.
- **Чому SD, а не стрім у serial**: потік 100 Гц × 6 осей через `Journal`
  потрапив би і в `ConsoleMqtt` (дзеркало журналу в брокер) — це забиття
  брокера сміттям. Окремий «сирий» шлях у serial повз журнал — ще один
  механізм виводу, якого правило KISS просить уникати.
- SD на C6 ділить SPI з дисплеєм — запис через `YIELD_DISPLAY_BUS()`, як
  усі SD-операції (`docs/architecture.md`, виноска ¹).
- Забрати датасет на ПК: витягти картку, або завантажити через портал, якщо
  на той момент буде роут для файлів SD (окремо не будуємо).
- **Протокол збору**:
  - 5–6 класів + обов'язковий клас `idle` (плату просто тримають, кладуть на
    стіл, беруть у руку, несуть) — без нього модель «впізнає» жест у
    кожному русі;
  - 40–60 повторів на клас, у кілька підходів, з різним хватом і швидкістю;
  - бажано — дві людини, інакше модель вивчить манеру одного.

### 1.3 Навчання (ПК)

`tools/ml/imu_train.py` (Python, numpy + scikit-learn; TensorFlow лише якщо
дійдемо до CNN):

1. **Базова лінія без нейромережі** — ознаки на вісь (mean, std, min, max,
   енергія, кількість перетинів нуля; 6 осей × 6 = 36 ознак) → logistic
   regression / random forest. Якщо дає ≥ 95% — це і є рішення.
2. **MLP** `36 → 32 → N` (ReLU, softmax): ~1.5 тис. параметрів, ~6 КБ у
   `float`. Нормалізація ознак (mean/std) експортується разом з вагами.
3. **1D CNN** на сирому вікні — лише якщо MLP не розрізняє схожі жести
   (коло vs «вісімка»). Тоді вже TFLite Micro (розділ 2).
- Валідація: окремий тестовий набір по **підходах**, а не випадкове
  перемішування (інакше повтори з одного підходу потрапляють і в train, і в
  test, і точність бреше). Звіт — матриця плутанини.
- Експорт: `tools/ml/export_header.py` → `src/Gesture/GestureModel.h`
  (`constexpr float` масиви, лягають у flash, RAM не займають).

### 1.4 Інференс на платі

- **Сегментація** (коли почався і скінчився жест): енергія гіроскопа
  `|g|` вище порогу → старт, ~150 мс тиші → кінець; вікно довше 2 с →
  відкинути. Пороги — з датасету, а не на око.
- MLP рахується власним кодом (~50 рядків: два матричні множення + ReLU +
  softmax), без TFLite: на 1.5 тис. параметрів це мікросекунди, а
  інтерпретатор TFLM коштував би десятки КБ heap на C6, де heap — найтісніше
  місце (див. пам'ять про heap C6).
- Поріг впевненості (напр. `conf < 0.8` → `unknown`), плюс клас `idle`.
- Бюджет: RAM ≤ 4 КБ (вікно + ознаки), flash ≤ 15 КБ. Заміряти `withTrace()`
  на `setupGesture()`.

### 1.5 Інтеграція

- Модуль `src/Gesture/` за зразком `src/Screen/`: `setupGesture()`,
  `registerGestureCommands()`, власний стан. `#if BOARD_HAS_IMU` — один раз
  навколо файлу.
- **Жест → команда через наявний `CommandQueue::submit()`**: прив'язки
  `gesture bind <gesture> "<command>"` в `ConfigStorage`. Жодного нового
  механізму дій — жест просто ще одне джерело команд, як serial і MQTT.
  Приклади: мах вправо → `next-screen`, коло → `dino`, стук-стук → `flip`.
- **Конфлікт з автофліпом**: поворот кистю на 180° — це рівно те, що ловить
  `ImuController` для перевороту екрана. Поки триває жест (сегментація
  активна), автофліп треба заморожувати.
- Команди: `gesture on|off`, `gesture status` (рівна табличка: клас,
  кількість розпізнань, середня впевненість), `gesture record`, `gesture bind`.
- Портал: рядок на картці System (або вкладка, якщо рядка буде мало) —
  увімкнено/вимкнено, остання подія, лічильники розпізнано/`unknown`.
- MQTT (опційно): `devices/<env>/gesture` з payload
  `{"g":"circle","conf":0.94}`, не retain — так жест може керувати чимось
  поза платою. Додати в `docs/mqtt-topics.md`.

### 1.6 Критерії готовності

- ≥ 90% точності на відкладених підходах, на кожному класі окремо.
- Не більше одного хибного спрацювання на годину звичайного поводження з
  платою (взяти, покласти, понести) — заміряти лічильником `unknown`/хибних.
- Мінус ≤ 5 КБ heap після `setupGesture()`.

### 1.7 Ризики

- Ручна розмітка «старт/кінець» у датасеті не збігається з автоматичною
  сегментацією на платі → модель вчилась не на тому, що бачить. Лікування:
  сегментувати датасет тим самим алгоритмом (на ПК, тим самим кодом).
- I²C-трафік FIFO гальмує тач. Заміряти час читання пачки; якщо тач
  «тупить» — менша пачка частіше.

## 2. Рукописні символи на `esp32-4848s040` (тач)

**Що робить:** користувач малює пальцем на екрані 480×480, плата впізнає
написане. Чотири доріжки, від простої до складної:

| Доріжка | Що | Чим | Де |
| :--- | :--- | :--- | :--- |
| **2A. Фігури-команди** | три крапки, галочка, хрест, коло, стрілка, «?», блискавка | шаблони `$P`, без нейромережі | плата, будь-яка з тачем (і C6) |
| **2B. Цифри** | 0–9 | CNN, MNIST | 4848s040 |
| **2C. Літери** | латиниця + українська кирилиця | CNN, EMNIST + CoMNIST + свої зразки | 4848s040 |
| **2D. Рукописний текст** | слова, речення | посимвольно на платі; суцільний текст — на rpi5 | 4848s040 (+ rpi5) |

Перша мета — 2A і 2B паралельно: 2A не потребує TFLM і дає корисну
функцію одразу, 2B — перевіряє TFLM на готовому датасеті.

**Чому друге:** даних можна взагалі не збирати (MNIST), і це перша справжня
згорткова мережа (CNN) у проєкті, тобто перша перевірка TFLite Micro з
ESP-NN на S3.

### 2.1 Димовий тест TFLite Micro

Перш ніж писати код розпізнавання — переконатись, що TFLM із фреймворку
взагалі збирається і лінкується в нашому PlatformIO-проєкті:

- мінімальна модель (класичний `hello_world` — апроксимація синуса) як
  serial-команда `ml selftest`;
- звірити: заголовки знаходяться без `-I`, `.a` лінкується, скільки
  займає `MicroInterpreter` + arena (заміряти `withTrace()`);
- результат — у «Карту коду» (`docs/architecture.md`, «Збірка:
  неочевидне»): як підключено, скільки коштує.
- Якщо прекомпільована бібліотека не підходить (версія, відсутні ops) —
  запасний варіант `lib_deps` на `tflm_esp32`/`Chirale_TensorFlowLite`.

### 2.2 Траєкторія з тача

- `TouchEvents` зараз не віддає точки під час руху. Додати один колбек
  `onMove(TouchPoint)` (кожен опитаний семпл, поки палець торкається) —
  мінімальна зміна, корисна не лише тут.
- Режим «полотно» (`ink on`), як режим `dino`: поки він активний, свайпи
  та кліки не перемикають екрани, а штрих малюється на дисплеї в реальному
  часі (пряма між сусідніми точками, товщина ~6 px).
- Буфер штриха — фіксований, `TouchPoint[512]` (4 КБ); кілька штрихів на
  символ («4», «Т»): символ закінчується через ~600 мс після останнього
  відпускання.
- ⚠ Частоту опитування GT911 з `loop()` заміряти: якщо < 30 Гц, швидкі
  штрихи будуть ламаними — тоді інтерполювати при растеризації.

### 2.3 Передобробка (MNIST-подібна)

Модель, навчена на MNIST, бачить білу цифру на чорному тлі 28×28, вписану в
20×20 і відцентровану за центром мас. Тому:

1. bounding box усіх штрихів → масштаб зі збереженням пропорцій у 20×20;
2. растеризація лініями з товщиною ~2 px і згладжуванням (MNIST — не
   1-піксельна лінія, інакше точність помітно падає);
3. центрування за центром мас у 28×28;
4. квантування в `int8` за параметрами вхідного тензора моделі.

Той самий код передобробки — і на платі, і в `tools/ml/` (для своїх
символів): розбіжність між ними — класична причина «на ПК 99%, на платі
70%».

### 2.4 Доріжка 2B: цифри — модель

- CNN: `conv 3×3 ×8 → maxpool → conv 3×3 ×16 → maxpool → dense 10`,
  int8-квантування після навчання. Очікувано ~10–20 тис. параметрів,
  ~20 КБ flash, arena ~20–40 КБ, інференс — одиниці-десятки мс на S3
  (заміряти, а не вірити).
- Arena — у внутрішній RAM, якщо влізе (швидше), інакше PSRAM.
- Навчання — `tools/ml/ink_train.py` (TensorFlow/Keras), експорт
  `.tflite` → `.h` масивом (`xxd -i` або скрипт).

### 2.5 Доріжка 2A: фігури-команди («три крапки → зроби дію»)

- **Алгоритм `$P Point-Cloud Recognizer`** (Vatavu та ін., 2012): фігура —
  хмара точок, порівняння з шаблонами за відстанню. Багатоштриховий і не
  залежить від порядку та напрямку штрихів — «хрест» можна малювати з будь-
  якого кута. ~200 рядків, без нейромережі, без датасету: **один-три
  шаблони на фігуру записує сам користувач** на платі.
- **Крапки — окремий швидкий шлях до `$P`**: якщо всі штрихи — дотики
  (bbox штриха < ~12 px), `$P` після нормалізації масштабу погано
  розрізняє «три крапки в рядок» і «три в стовпчик». Тому: кількість
  крапок + розташування (рядок / стовпчик / трикутник / квадрат) —
  простими правилами. Це окремий словник: `•••`, `⋮`, `∴`, `::`.
- Стартовий словник (прив'язки змінювані):

  | Фігура | Дія за замовчуванням |
  | :--- | :--- |
  | `•••` три крапки в рядок | меню команд на екрані |
  | `⋮` три крапки в стовпчик | `status` |
  | ✓ галочка | підтвердити поточне |
  | ✗ хрест | скасувати / вийти з режиму |
  | ○ коло | оновити екран |
  | → / ← стрілка | наступний / попередній екран |
  | `?` | довідка по фігурах |
  | ⚡ блискавка (зигзаг) | `reboot` — **лише з підтвердженням** галочкою |

- Команди: `ink shape add <name>` (наступний малюнок стає шаблоном),
  `ink shape list|del`, `ink bind <name> "<command>"`. Шаблони — JSON у
  LittleFS (NVS для десятків шаблонів по кількасот байт тісний). ⚠
  `uploadfs` стирає розділ разом із шаблонами (див. пам'ять про
  WiFi-профілі), тому потрібен `ink shape export` у serial для бекапу.
- Поріг: фігура приймається лише при чіткому збігу; інакше малюнок іде
  далі — на розпізнавання символу (2B/2C). Так один і той самий режим
  полотна приймає і команди, і текст без перемикачів.

### 2.6 Доріжка 2C: літери

- **Латиниця** — EMNIST Letters (26 класів, той самий формат 28×28).
- **Кирилиця** — CoMNIST (Cyrillic-oriented MNIST, ~15 тис. зразків). ⚠ У
  ньому може бракувати `і ї є ґ` — їх добрати власними зразками через
  `ink record <label>` (`/ml/ink/<label>/<NNN>.pgm` на SD, PGM —
  найпростіший формат). 40–60 зразків на відсутню літеру, від 2+ людей.
- **Неусувні пари**: `0/O/О`, `3/З`, `B/В`, `p/р`, `c/с`, `x/х`, `6/б`.
  Вони пишуться однаково, і жодна модель їх не розрізнить. Розв'язок — не
  в моделі, а в режимі: перемикач `123` / `ABC` / `АБВ` на полотні, і
  модель повертає топ-3, з яких режим вибирає дозволений.
- Модель: одна CNN на всі класи (~10 цифр + 26 + 33 ≈ 70 класів) або три
  окремі, по одній на режим. Почати з трьох окремих: менші, точніші, і
  кожну можна навчати незалежно. Очікувано ~30–60 КБ int8 кожна — на S3 з
  4 МБ app-розділу не обмеження.
- ⚠ Вивід кирилиці на дисплей 4848s040: чи є в поточному графічному
  бекенді шрифт з кирилицею — перевірити до цього етапу.

### 2.7 Доріжка 2D: рукописний текст

Розпізнати «суцільний» рукопис (слова, прописом) на ESP32 нереально: це
моделі послідовностей (CRNN + CTC, трансформери) у десятки-сотні МБ. Тому
два рівні:

1. **Посимвольно на платі** (як Palm Graffiti): пишемо по літері в одне
   поле, кожна розпізнається через 2C, текст набирається в рядку
   над полотном. Пробіл — мах вправо, видалити — мах вліво (свайпи вже є в
   `TouchEvents`). Корекція за словником — опційно: невеликий список слів
   у LittleFS і вибір серед топ-3 кандидатів на кожну літеру.
2. **Суцільний текст — на rpi5**: плата растеризує все полотно в PNG і шле
   його на rpi5 (HTTP), там модель рукописного OCR (напр. TrOCR, сотні МБ,
   секунди на рядок на Pi 5) або хмарне API. Результат повертається назад.
   Це вже не «ML на ESP32», а ESP32 як клієнт; робити лише після 1 і
   лише якщо 1 виявиться незручним. Мережевий запит блокуючий — через
   `WebJobQueue`/`loop()`, не з колбеку тача.

### 2.8 Інтеграція

- Модуль `src/Ink/`, `#if` за власним `HAS_INK_RECOGNIZER` у
  `src-4848s040/environment.h` (розділ 2 файлу). `$P` (2A) — окремо від TFLM
  і може вмикатися і на C6 (`esp32-c6`, тач 172×320): там поле мале, але
  для фігур досить.
- Розпізнана фігура або символ → `CommandQueue::submit()` через прив'язки,
  як у жестах. На цьому етапі в жестах і в рукописі будуть дві однакові
  таблиці «подія → команда» — це і є момент винести її в спільне місце
  (другий користувач).
- Розпізнаний текст (2D) — куди саме його дівати, вирішити на етапі: у
  поле вводу команди (тобто «написати команду пальцем»), у MQTT
  `devices/<env>/ink/text`, у буфер для пошти `GmailSender`.
- Портал: рядок «Ink: N фігур / N символів, остання `7` (0.97)».

### 2.9 Критерії готовності

- 2A: ≥ 95% на 8 фігурах з шаблонами від того ж користувача; ≤ 1% фігур
  помилково приймаються за команду (особливо небезпечна блискавка).
- 2B: ≥ 95% на цифрах, намальованих на самій платі (не на тестовому
  MNIST), щонайменше 20 зразків на цифру від двох людей.
- 2C: ≥ 90% у межах режиму (`ABC` / `АБВ`).
- Від відпускання пальця до результату на екрані ≤ 100 мс (крім 2D/rpi5).

## 3. Wi-Fi CSI: присутність і рух у кімнаті

**Що робить:** плата без жодного датчика визначає, чи є хтось у кімнаті і чи
рухається він, за спотвореннями радіоканалу між нею і роутером.

**Що таке CSI.** Channel State Information — «стан каналу». Wi-Fi-кадр
(OFDM) передається одночасно на багатьох піднесучих: у каналі 20 МГц їх 64,
з них ~52 несуть дані. Кожен приймач для кожного кадру оцінює, як канал
змінив амплітуду й фазу на кожній піднесучій, — без цього він не декодує
кадр. ESP32 віддає цей масив (комплексне число на піднесучу) у колбек.
Радіохвиля доходить до приймача кількома шляхами — напряму і відбита від
стін, меблів, людей; людина рухається — змінюються відбиття — «плаває»
CSI. RSSI — одне число (сумарна потужність), надто грубе; CSI — ~52 числа
на кадр, тобто набагато детальніший «відбиток» кімнати. Зображення це не
дає і людину не впізнає — лише «щось у полі між TX і RX змінилось і як».

**Чому третім:** найцікавіше й найменш передбачуване. Дані шумні, модель
прив'язана до конкретної кімнати й розстановки меблів, тож результат не
гарантований — варто йти тоді, коли цикл ML уже відпрацьовано на 1 і 2.

### 3.0 Один env для CSI-плат, ідентичність — у NVS

Чинний `env:esp32-c3` під CSI не чіпаємо, а додаємо **один** новий —
`env:esp32-c3-csi` (`extends = env:esp32-c3`, власний
`src-esp32-c3-csi/environment.h`). Три плати прошиваються однією збіркою,
а відрізняються записами в NVS.

**Навіщо окремий env узагалі** (а не прапорець у `env:esp32-c3`):

1. Робоча плата. `env:esp32-c3` уже може працювати як плата
   EcoFlow-проксі — ML-експерименти не мають змінювати її прошивку.
2. Ресурси. C3 без PSRAM; CSI-кільце, ESP-NOW і UDP-стрім вимагають
   heap, тому з CSI-прошивки прибирається непотрібне через `HAS_*` у її
   `environment.h` (розділ 2 файлу: `HAS_CSI_SENSOR 1`,
   `HAS_ECOFLOW_CLIENT 0`, `HAS_GMAIL_SENDER 0`, …).

**Чому один env, а не два** (`-tx`/`-rx`): механізм ідентичності в NVS
уже є, а env, що відрізняються лише назвою, — довша повна збірка і
ризик прошити «не той» env на плату.

| Що | Звідки зараз | Що треба для двох плат |
| :--- | :--- | :--- |
| префікс топіків | `MQTT_TOPIC_PREFIX`, override у NVS `mqtt.prefix` (команда `mqtt-prefix`, діє після reboot) | **є.** Лише через слеш: `mykola-lavryk/rx` — ACL на rpi5 дозволяє `mykola-lavryk/#`, а `mykola-lavryk-rx` вийде за його межі, і брокер мовчки відхилить підписки |
| client id | `MQTT_CLIENT_ID = "mqtt-${PIOENV}"`, лише компіляція | **бракує.** Однаковий client id на двох платах = брокер вибиває їх одна одною по колу. Макрос вклеєний у ~12 топіків літералом (`docs/architecture.md`, «MQTT topic-префікс»), тому повний перехід на runtime — не мала зміна. **Мінімум:** override у NVS (`mqtt.client-id`) лише для client id **підключення** (`config.clientId`, `src/App/AppGlobals.cpp`); сегмент `<id>` у топіках лишається `mqtt-esp32-c3-csi`, а топіки двох плат розводить префікс |
| hostname | `net general hostname` | є, переживає ребут (`saveConfig()`) |
| роль `tx`/`rx` | — | нова, NVS `csi.role` |
| акаунт на rpi5 | один `user` на env | один спільний акаунт на обидві плати — достатньо, ACL і так за префіксом |

- **Одна команда на всю ідентичність**: `csi setup <tx|rx>` пише
  роль, префікс `mykola-lavryk/<name>`, client id підключення
  `mqtt-esp32-c3-csi-<name>` і hostname, потім reboot. Чотири окремі ручні кроки на кожну плату — це
  гарантія, що на одній із них якийсь забудуть.
  Загальна serial-команда `nvs set` (`docs/tech_debt.md`, «Читання й
  запис NVS з shell») цього не замінює, а доповнює: нею зручно звірити
  чи поправити окремий ключ з shell через `./esp`.
- **Захист від забутого кроку**: поки `csi setup` не виконано, плата не
  вмикає ні MQTT, ні CSI, а пише `[W] csi: identity not set, run 'csi setup'`
  і показує це на порталі. Так «забута» плата видна одразу, а не по
  вибиванню сусіда з брокера.
- **«Прошивка для навчання» і «робоча» — одна й та сама.** Запис датасету —
  це просто команда `csi record`, а не окрема збірка. Інакше модель
  працювала б на іншій прошивці, ніж та, що збирала дані: інші таймінги,
  інший heap, ризик розбіжності в обчисленні ознак.
- Для `esp32-c6` (жести) і `esp32-4848s040` (рукопис) окремий env **не
  потрібен**: там по одній платі, і фіча вмикається прапорцем `HAS_*` у
  їхньому `environment.h`.
- **Назва env — `esp32-c3-csi`, а не `csi`.** Незалежна від плати тут
  фіча (`HAS_CSI_SENSOR`), а env у PlatformIO завжди прив'язаний до одного
  чипа (`board`, розділи флешу, `src-<env>/`). Назва без чипа збреше, щойно
  CSI з'явиться на другій платі (`esp32-s3-lcd147`), і не підкаже, на
  який чип це шиється (чужий env на C6 уже давав boot-loop).
- ⚠ **`./esp` не знайде порт для env з `extends`**: `port_for_env()` бере
  `board =` лише з тексту самої секції `[env:…]`, успадкованого не бачить.
  Або повторити `board = …` у секції нового env (з коментарем чому), або
  навчити `./esp` спершу питати `pio project config`.
- Разом з новим env: запис у матриці фіч (`docs/architecture.md`), акаунт
  і ACL на rpi5 (`docs/ecoflow_mqtt_proxy_setup.md`, «Реєстрація нової
  плати»), override client id — у `docs/architecture.md`, розділ «MQTT
  topic-префікс», і в `docs/mqtt-topics.md` (топіки з префіксом
  `mykola-lavryk/<name>/…`).

### 3.1 Топологія: дві `esp32-c3` + rpi5

C3 у наявності три, але одна — робоча плата EcoFlow-проксі, і її в CSI не
залучаємо (ні як TX, ні як RX: це змінило б її прошивку). Лишаються дві.

CSI знімається з кожного прийнятого кадру, тому потрібен **рівномірний
потік кадрів від нерухомого передавача**. Роутер тут поганий передавач: його
трафік нерівномірний, а щоб він слав 100 кадрів/с, його треба ще й пінгувати.
Своя C3 робить це краще:

```
   [C3-TX] біля роутера/rpi5     ESP-NOW broadcast, 100 кадрів/с
      │  ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ┐
      │        зона, де ходять люди            ▼
   [роутер] ─ ─ відповіді на пінг (траса 2) ─→ [C3-RX] інший бік кімнати
                                                 │ CSI → ознаки → стан
                                                 └─ UDP (лише під час запису) ─→ [rpi5] колектор, навчання
```

- **C3-TX** — стоїть біля роутера/rpi5, живлення постійне. Шле
  ESP-NOW broadcast із фіксованою частотою і лічильником кадрів (щоб RX
  бачив втрати). ESP-NOW не навантажує роутер і не залежить від його
  трафіку. TX лишається підключеним до Wi-Fi (портал, прошивка), і тому
  ESP-NOW автоматично йде на каналі роутера — RX, теж підключений до
  Wi-Fi, сидить на тому самому каналі.
- **C3-RX** — з протилежного боку кімнати, так щоб люди ходили між ним і
  TX. Основна траса — кадри TX (фільтр у колбеку за MAC TX).
- **Друга траса без третьої плати**: той самий RX може паралельно знімати
  CSI з відповідей роутера на пінг (~20–50/с) — окреме кільце за MAC
  роутера. Дві траси з різних напрямків — це те, що дали б два приймачі,
  хоч і гірше (роутер відповідає нерівно). Вмикати, лише якщо однієї
  траси для етапу 2 з 3.3 не вистачить.
- **Розширення пізніше**: другим RX може стати `esp32-s3-lcd147` (той
  самий формат CSI Wi-Fi 4) — фіча вмикається прапорцем `HAS_CSI_SENSOR` у
  його `environment.h`, окремий env не потрібен.
- **rpi5** — колектор датасету (UDP-приймач, пише файли), там же
  навчання (`tools/ml/csi_*.py` запускаються на ПК чи на rpi5 — однаково).
  Саме інференс — на RX, щоб присутність працювала і без rpi5.
- **Одна прошивка на дві C3** (`env:esp32-c3-csi`), роль і ідентичність —
  у NVS через `csi setup`, див. 3.0.
- `WiFi.setSleep(false)` на RX і TX — power save губить кадри.
- Радіо належить `NetworkSupervisor`: CSI і ESP-NOW вмикаються з `loop()`
  після підключення, **не під `_mutex` NS** (див. пам'ять про дедлок
  `WiFi.*`).
- Запасний режим без TX — RX шле ~50 пінгів/с на роутер і знімає CSI з
  відповідей. Гірше (роутер відповідає нерівно), але дозволяє почати з
  однієї плати.

### 3.2 Збір

- Колбек `esp_wifi_set_csi_rx_cb()` виконується в контексті Wi-Fi таска —
  там лише фільтр за MAC і копія амплітуд (до 64 піднесучих, `int8` re/im
  → амплітуда `uint8`) у fixed-size кільце (128 записів × ~70 Б ≈ 9 КБ — на
  C3 без PSRAM більше не варто) і лічильник переповнень. Жодного логу чи
  heap у колбеку.
- `loop()` рахує ознаки за вікно 1 с: дисперсія амплітуди по піднесучих,
  середня зміна між сусідніми кадрами, частка втрачених кадрів (за
  лічильником TX).
- **Запис датасету — UDP на rpi5**, не SD: на C3 SD немає. `csi record
  <label> <sec> <host>:<port>` — пакети по ~20 кадрів, ~7–14 КБ/с на RX.
  На rpi5 — `tools/ml/csi_collector.py`: приймає, пише
  `.cache/ml/csi/<board>/<label>/<час>.bin`, рахує втрати. Через MQTT чи
  журнал цей потік не ганяти (з тієї ж причини, що в 1.2). UDP-стрім —
  новий «прихований» канал, тому його стан (вкл/викл, куди, байт/с,
  помилок send) — на порталі (правило видимості).
- Розмітка: під час запису — серія сесій по 5–10 хв на клас (`empty` —
  нікого вдома; `still` — сидять за столом; `moving` — ходять), у різний
  час доби (зміни інтерференції від сусідів).

### 3.3 Етапи

1. **Детектор руху без ML**: дисперсія ознаки за вікно > поріг → «рух».
   Графік ознаки на порталі в реальному часі — без нього поріг не
   підібрати. Часто вже цього досить для «є рух / нема».
2. **Класифікатор стану**: класи `empty` / `still` (людина сидить) /
   `moving`, сесії по 5–10 хв на клас у різний час доби. Ознаки → random
   forest → C-код через `emlearn` або `m2cgen` (дерева — це `if`-и, без
   TFLM і майже без RAM). `still` проти `empty` — найважча пара: саме тут
   видно, чи CSI справді щось дає.
3. (Опційно) Підрахунок людей, місце в кімнаті — лише якщо 2 спрацює
   стабільно; висока ймовірність, що ні.

### 3.4 Інтеграція

- Портал: стан (`empty`/`still`/`moving`), впевненість, пакетів/с,
  переповнень кільця — це якраз «прихований канал», який за правилом
  обов'язково має бути видимим.
- MQTT `devices/<env>/presence` retain — для автоматизацій (вимкнути
  підсвітку дисплеїв, коли в кімнаті порожньо). У `docs/mqtt-topics.md`.

### 3.5 Ризики

- **Дві C3 з однаковою MQTT-ідентичністю** вибивали б одна одну з брокера
  (однаковий client id). Закривається ідентичністю в NVS (3.0); до появи
  override client id друга C3 на брокер не підключається.
- **Плату проксі не переплутати.** Усі три C3 зовні однакові, а прошивка
  `env:esp32-c3-csi` на платі проксі мовчки зупинить EcoFlow-проксі.
  Підписати плати фізично і перед прошивкою звіряти, що на порту не
  проксі (`./esp` без ресету: подивитись hostname/env у `status`).
- Модель перестає працювати після перестановки меблів чи зміни каналу
  роутера — потрібна команда `csi calibrate` («кімната порожня, запам'ятай
  фон»).
- ESP-NOW 100 кадрів/с займає частку ефіру каналу роутера — заміряти, чи
  не просідає швидкість інших пристроїв; за потреби 50 кадрів/с.
- C3 — Wi-Fi 4, формат CSI класичний (HT-LTF), добре задокументований; на
  C6 у 802.11ax (HE-LTF) він інший — тому для CSI саме C3, а не C6.

## 4. Датчик світла на `esp32-st7789`

**Що вже є** (`src/Screen/ScreenControl.cpp`, `setupLightSensor()`): `AnalogSensor` на
GPIO34, `update()` з cron-таска з інтервалом 0 (тобто щоітерації `loop()`),
сирий діапазон 0–1855 → 0–100%, колбек при зміні ≥ 5%. Значення
публікується в MQTT `devices/<client-id>/light-sensor` (інші плати на нього
підписані й логують), керує режимом `brightness auto` і видно на екрані.

Один канал, одне число — тому тут ML здебільшого не про розпізнавання
форми, а про **підлаштування під людину й аналіз часового ряду**.

### 4.1 Яскравість, що вчиться (навчання прямо на платі)

Зараз `brightness auto` — фіксована пряма «світло → яскравість». Людині
вона зазвичай не підходить: вночі заяскраво, на сонці затемно. Так само
влаштована Adaptive Brightness в Android — і там це саме ML.

- Кожна ручна корекція `brightness N` у режимі auto — це **мітка**: «при
  освітленні L (і годині H) я хочу N». Пара `(L, H, N)` пишеться в кільце в
  NVS (≈ 64 записи × 4 Б).
- Модель — **кусково-лінійна крива** на 8–10 вузлах по осі освітлення,
  монотонна (більше світла → не темніше). Підгонка — найменші квадрати з
  обмеженням монотонності (isotonic regression, алгоритм PAVA, ~40 рядків),
  **просто на платі**, після кожної нової мітки, за мілісекунди. Це
  єдиний варіант у плані, де навчання відбувається на самому ESP32, без
  ПК.
- Старі мітки «забуваються» (вага спадає з віком) — уподобання зсуваються
  із сезоном.
- Година як друга ознака — лише якщо дані покажуть, що одне й те саме
  освітлення ввечері і вдень людина хоче по-різному.
- Команди: `brightness learn status` (крива рівною табличкою: вузол, L,
  яскравість, кількість міток), `brightness learn reset`. Портал: кількість
  міток, вік останньої.
- ⚠ **Підсвітка може засвічувати сам датчик**: фоторезистор на лицьовому
  боці поруч з екраном, і якщо світло підсвітки (`TFT_BL` 21) потрапляє на
  нього, виходить петля «яскравіше → датчик бачить більше світла → ще
  яскравіше». Перевірити до будь-якої моделі: у темряві міряти
  `lightSensor.read()` при яскравості 0, 50, 100. Якщо залежність є —
  віднімати внесок підсвітки (калібрувальна таблиця з того ж заміру).

### 4.2 Жести тінню над датчиком

Рука над датчиком — тінь, і її форма в часі — сигнал:

| Жест | Сигнал | Приклад дії |
| :--- | :--- | :--- |
| мах | короткий провал 100–400 мс | наступний екран |
| подвійний мах | два провали за ≤ 800 мс | `dino` |
| накрити й тримати | провал > 1 с | вимкнути / ввімкнути екран |
| повільно наблизити | плавне падіння | приглушити |

- Безконтактне керування для плати, де тач є, але руки бувають брудні
  (кухня, майстерня).
- Перший крок — **без ML**: провал відносно ковзного фону (а не
  абсолютний поріг — фон удень і вночі різний), тривалість і кількість
  провалів. Модель (той самий MLP, що в 1.3, на одному каналі) — лише
  якщо правила плутатимуть мах і зміну освітлення в кімнаті.
- Потрібен рівномірний потік семплів ~100 Гц: зараз `update()` іде
  щоітерації `loop()`, тобто нерівно. Для жестів — окремий `addCronTask(10, …)`
  і власне коротке кільце, щоб не чіпати існуючу логіку 5%-порогу.
- Не працює в темряві (нема що затіняти) — це межа фізики, не баг; у
  статусі показувати «gesture: unavailable (too dark)».
- Під час жесту `brightness auto` має ігнорувати провали, інакше екран
  блимає під руку (так само, як автофліп заморожується в 1.5).

### 4.3 Тип освітлення за мерехтінням

Світло від мережі мерехтить на 100 Гц (50 Гц × 2), сонце — ні, LED-лампи —
залежно від драйвера. Якщо зняти 1 с з частотою ~2 кГц і подивитись спектр,
можна відрізнити `daylight` / `lamp` / `dark` — без людської розмітки, за
фізичною ознакою.

- ⚠ **Сумнівно для фоторезистора**: CdS реагує за десятки мс і 100 Гц
  сильно згладжує. Тому спершу — експеримент на 10 хвилин: команда
  `light scope` (2000 семплів у буфер, потім вивести амплітуду на 100 Гц
  при лампі й при денному світлі). Немає різниці — ідею закриваємо,
  записавши результат сюди.
- Якщо працює — «лампа ввімкнулась» стає подією для MQTT і ознакою для
  присутності.

### 4.4 Спільно з CSI і часом доби

Світло вже публікується в MQTT, тож його бачать інші плати. Пізніше —
ознака для моделі присутності з розділу 3: «вечір + світло ввімкнене» і
«вечір + темно» — різні апріорні ймовірності, що в кімнаті хтось є. Лише
якщо кімната датчика і кімната CSI — одна й та сама.

### 4.5 Порядок

4.1 перевірка засвітки від підсвітки (10 хв) → 4.3 експеримент
`light scope` (10 хв, відповідає «так/ні») → 4.1 крива, що вчиться →
4.2 жести тінню без ML.


## 5. Аномалії в телеметрії (EcoFlow, heap)

**Висновок: ML тут не потрібен.** Задача — помітити «DELTA 2 замовкла»,
«heap повільно тече», «вихідна потужність дивно скаче». Це закривають
статистичні методи без моделі:

- **тиша**: таймаут з урахуванням режиму (терміни «активна»/«мовчить» —
  вже визначені для DELTA 2: 1–3 с проти 10–15 хв);
- **дрейф**: EWMA і лінійний тренд `heapFree` за години;
- **викиди**: z-score / межа ±3σ від ковзного середнього потужності.

Записано тут, щоб варіант не здавався пропущеним. Якщо колись знадобиться —
це окрема задача моніторингу, а не ML; кандидат у `docs/tech_debt.md`, якщо
«тиха» DELTA 2 повториться.

## 7. Поза планом (потрібне залізо)

- **Голос (keyword spotting)**: I²S-мікрофон INMP441 (~$2) на S3. В
  arduino-esp32 для S3 є `ESP_SR` (WakeNet/MultiNet) — готове «Hi ESP» і
  команди без навчання. Своє слово — через TFLM, як у розділі 2.
- **Зір**: S3 з камерою (ESP32-S3-EYE-подібна плата) + ESP-DL — детекція
  облич/людей. Інший клас задач і пам'яті.

## 8. Відкриті питання
