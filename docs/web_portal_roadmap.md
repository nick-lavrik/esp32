# Веб-портал: що лишилось зробити

Стан на 14.09.2026. Каркас і два розділи (Wi-Fi, Console) зроблені й перевірені
на залізі — див. `docs/web_portal.md`. Тут лежить решта плану, щоб повернутись
до неї без відновлення контексту.

Вихідний список розділів (як його сформулював власник):

- [x] стартує незалежно від підключення до WiFi (AP-fallback, вебка на точці)
- [x] налаштування wifi
- [ ] розділ команд: список / запуск / shortcut («вільний» список команд з параметрами)
- [ ] CRUD LittleFS
- [ ] CRUD NVS
- [x] console (відображення serial і відправка команд)
- [ ] відображення екрана

## Незмінні правила, які діють для кожного нового розділу

Це не стиль, а те, на чому вже обпеклись. Порушення дає або мертвий сервер,
або дедлок WiFi-стека.

1. **Розділ — це `IWebModule`.** `registerRoutes()` викликається до
   `HttpServer::begin()`, `loop()` — з контексту `loop()` пристрою.
2. **Мутації — тільки через `WebJobQueue`.** У таску AsyncTCP не можна нічого,
   що блокує: `WiFi.*`, запис у NVS/flash, друк сотень рядків, звернення до
   шини дисплея. HTTP відповідає `202 {"jobId": N}`, клієнт опитує
   `GET /api/job?id=N`.
3. **Читання — зі знімка, який готує `loop()`,** якщо джерело даних живе під
   чужим мьютексом або може бути перевиділене (як вектор з'єднань
   `NetworkSupervisor`).
4. **Перед новим публічним класом у `lib/` — перевірити ім'я на колізію**
   (див. розділ про ODR у `docs/web_portal.md`):
   ```sh
   grep -rl "class <Name>\b" \
     ~/.platformio/packages/framework-arduinoespressif32/libraries \
     .pio/libdeps/<env>
   ```
5. **Вивід — англійською** (правило проєкту, `CLAUDE.md`), коментарі —
   українською.
6. **Після правки `data/www/` — `./tools/gen_web_assets.py`**, інакше вшита
   копія розійдеться з тією, що в LittleFS.
7. **Стежити за флешем.** App-розділ на обох C6 — 2 МБ. Після кожного розділу
   міряти: `pio run -e <env>` з `-D HAS_WEB_PORTAL=0` і без, різниця = ціна.
   Запас: `esp32-c6` ~137 КБ, `esp32-c6-lcd096` ~317 КБ.

## Розділ «Команди»

Основа вже є: `GET /api/console/commands` віддає ім'я + опис кожної
зареєстрованої команди (`SerialCommander::commandCount()/commandName()/
commandDescription()` додані в цій ітерації), а `POST /api/console/exec`
виконує рядок через чергу.

Лишилось:

- окрема вкладка зі списком команд і пошуком (зараз список живе лише як
  `<datalist>` для автодоповнення в консолі);
- форма запуску з параметрами: поле аргументів + кнопка, вивід — у ту саму
  стрічку логу;
- **shortcuts** — вільний список «назва + рядок команди», який редагує
  користувач. Зберігати в NVS: один ключ `web_shortcuts` через
  `ConfigStorage::setStringArray()` (обмеження ключа NVS — 15 символів).
  Формат елемента — `<назва>\t<команда>`, щоб не тягнути JSON-парсер на
  пристрій. API: `GET/POST /api/shortcuts`, `DELETE /api/shortcuts?index=N`.
  Запис у NVS — через чергу задач.

Ризик: `SerialCommander::execute()` виконується в `loop()` і може блокувати
кадр на секунди (`sdbench`, `sdmap`, `scan`). Це прийнятно — так само
поводиться serial-консоль, — але сторінка має показувати «виконується», поки
задача не `done`.

## Розділ «CRUD LittleFS»

API (усі мутації — через чергу, бо це flash I/O):

| Метод | Шлях | Дія |
|---|---|---|
| GET | `/api/fs/list?path=/` | список: ім'я, розмір, чи каталог |
| GET | `/api/fs/read?path=...` | віддати файл (`request->send(LittleFS, path)`) |
| POST | `/api/fs/upload` | завантажити файл (`onUpload`-хендлер) |
| POST | `/api/fs/mkdir` | створити каталог |
| DELETE | `/api/fs/remove?path=...` | видалити файл або каталог |
| POST | `/api/fs/rename` | `from`, `to` |
| GET | `/api/fs/info` | used / total / free |

Чого остерігатись:

- **Завантаження великих файлів.** `onUpload` у ESPAsyncWebServer приходить
  порціями в таску сервера, і писати їх треба одразу у відкритий `File` —
  накопичувати в RAM не можна (фонові JPEG бувають по 270 КБ). Це єдиний
  виправданий виняток із правила «нічого важкого в таску сервера»: черга тут
  не допоможе, бо дані течуть саме звідти. Файл відкривати на першій порції
  (`index == 0`), закривати на `final`.
- **Захист від виходу за корінь**: відкидати шляхи з `..` і без провідного `/`.
- **`/www` редагується тим самим CRUD** — тобто можна знести власну вебку.
  Вшита копія в PROGMEM це страхує, але попередження в UI не завадить.
- SD-картка (`BOARD_HAS_SD`) — той самий модуль з іншим `fs::FS&`; варто
  одразу закласти параметр джерела (`?fs=littlefs|sd`), а не хардкодити.

## Розділ «CRUD NVS»

**Блокер:** `ConfigStorage` не вміє видаляти один ключ — є лише `clearAll()`.
Треба додати `bool remove(const char* key)`: на ESP32 це
`Preferences::remove()`, на ESP8266 — `LittleFS.remove(pathFor(key, ext))`
(файлова реалізація, див. `ConfigStorage.cpp`).

Решта вже є: `listEntries()` віддає ключ + тип, `getType()`, `typeToString()`,
типізовані геттери/сеттери.

API:

| Метод | Шлях | Дія |
|---|---|---|
| GET | `/api/nvs/list` | ключі поточного namespace з типами |
| GET | `/api/nvs/get?key=...` | значення (за типом з `getType()`) |
| POST | `/api/nvs/set` | `key`, `type`, `value` |
| DELETE | `/api/nvs/remove?key=...` | видалити ключ |

Чого остерігатись:

- namespace — це `PIO_PIOENV`; той самий, у якому `NetworkSupervisor` тримає
  `nm_config` / `nm_connections`. Правка цих ключів руками ламає мережу —
  позначати їх у UI як системні;
- blob-типи (`NVS_TYPE_BLOB`) показувати лише як «binary, N bytes» без спроби
  редагувати: за ними стоять `setStruct()`-структури з magic/version;
- обмеження ключа — 15 символів ASCII (`ConfigStorage::isKeyValid()`), UI має
  перевіряти це до відправки;
- `web_user` / `web_pass` лежать у тому ж namespace: через цей розділ можна
  зняти з себе авторизацію. Або ховати ці ключі, або вимагати підтвердження.

## Розділ «Відображення екрана»

Схема, яку обрав власник (і вона справді найдешевша): **не збирати повний кадр
на пристрої**. `Display` малює через спрайт однієї смуги
(`DISPLAY_SPLIT_COUNT`), повного фреймбуфера в RAM немає і не треба —
віддавати поточну смугу разом з її індексом, а повний екран збирати в
браузері, тобто дублювати `display.flush()` на клієнті.

Що для цього є в `Display`:

- `splitCount()` — скільки смуг складають кадр;
- `splitIndex()` — індекс смуги, яку малює поточна ітерація `loop()`;
- `splitHeight()`, `width()`, `height()`;
- `isFrameStart()` — true рівно раз на кадр.

План:

1. Розділ вмикається **тільки при `DISPLAY_SPLIT_COUNT > 0`** — інакше
   спрайта немає і віддавати нічого (на `esp32-c3` саме так).
2. `GET /api/screen/info` → `{width, height, splitCount, splitHeight, depth}`.
   `depth` брати з `SPRITE_COLOR_DEPTH` (16 на C6, буває 8/RGB332).
3. `GET /api/screen/strip` → сирі байти поточної смуги + заголовки
   `X-Split-Index`, `X-Split-Count` (або перші байти тіла). Клієнт малює їх у
   `<canvas>` зі зсувом `index * splitHeight`.
4. Дістати піксели зі спрайта: у гілці TFT_eSPI — `TFT_eSprite::getPointer()`,
   у гілці Arduino_GFX (C6) — власний буфер канви; треба додати в `Display`
   метод `const void* spriteBuffer() const` + `size_t spriteBufferSize() const`,
   розгалужений тим самим `#if`, що й `sprite()`.
5. **Синхронізація.** Читати буфер у таску сервера, поки `loop()` його малює,
   не можна — буде рваний кадр. Варіант: на запит виставити прапорець, а в
   `loop()` після `endWrite()` скопіювати смугу в окремий буфер (розмір однієї
   смуги, не кадру) і віддати з нього. Це те саме правило №2, тільки замість
   черги задач — прапорець і буфер на одну смугу.
6. Оцінити трафік: 172×320 RGB565 = 110 КБ на повний кадр. Для «живого» екрана
   це багато — почати з кнопки «зняти кадр», а не з потокового оновлення.
   RGB332 (`SPRITE_COLOR_DEPTH=8`) удвічі дешевший, але на C6 канва
   Arduino_GFX 8bpp не має (див. коментар до `pushImage8bpp()` у `Display.h`).

## Дрібне, що варто прибрати принагідно

- `HttpServer::setTemplateResolver()` — заглушка, `ITemplateResolver` не
  реалізований; або дописати, або прибрати разом із полем.
- `src/netcli.h:626` — чотири попередження `-Wformat` (`%u` проти
  `long unsigned int`) у `cidrToMask()`. Не наше, але шумить у кожній збірці.
- Портал зараз увімкнений лише на двох C6-env. `esp32-4848s040` і
  `esp32-s3-lcd147` мають ESPAsyncWebServer у `lib_deps` і PSRAM — там він
  теж має сенс, треба лише зміряти флеш.
