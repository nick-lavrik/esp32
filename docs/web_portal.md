# Веб-портал пристрою

Портал — це `lib/WebPortal` поверх `lib/HttpServer` (ESPAsyncWebServer).
Вмикається прапорцем `-D HAS_WEB_PORTAL=1` у `build_flags` конкретного env;
зараз він стоїть на **всіх платах, крім `esp8266`** — тобто на семи ESP32.
Виняток не в лінощах: на `esp8266` портал технічно збирається, але з'їдає RAM,
якої там і без нього лишається ~15 КБ (розбір — `docs/architecture.md`,
підрозділ «Веб-портал на ESP8266»).

Реалізовано два розділи: **Wi-Fi** і **Console**. Решта зі списку (команди,
CRUD LittleFS, CRUD NVS, відображення екрана) підключається як нові
`IWebModule` без змін у самому порталі — план і застереження до кожного
розділу лежать у `docs/web_portal_roadmap.md`.

## Головна властивість: портал не залежить від мережі

`setupWebPortal()` піднімає сервер один раз у `setup()` і ніколи не гасить.
`AsyncWebServer` слухає на всіх інтерфейсах lwIP, тому та сама інстанція
обслуговує і домашню мережу, і точку доступу, яку `NetworkSupervisor`
піднімає сам, коли жодної збереженої мережі не видно (AP-fallback,
SSID `ESP-<env>`, адреса `192.168.4.1`).

Прив'язувати старт сервера до `WiFi.isConnected()` не можна: саме тоді, коли
мережі немає, портал і потрібен.

## Чому все важке виконується в `loop()`

Обробники ESPAsyncWebServer крутяться у власному таску. Майже все, що робить
портал, для такого таску отруйне:

- `NetworkSupervisor::scan()` блокує на 2–3 с (власний цикл очікування
  `WiFi.scanComplete()`);
- `connectTo()` / `startAp()` смикають блокуючі `WiFi.*`, а ті чекають на
  arduino event task — рівно той дедлок, який описаний у `NetworkSupervisor.hpp`;
- `saveConfig()` — це запис у NVS, тобто flash I/O;
- serial-команда може надрукувати сотні рядків або полізти на шину дисплея,
  яку `loop()` тримає відкритою через увесь кадр.

Тому кожна мутація лише **кладеться в чергу** (`WebJobQueue`), а виконується
в `loop()` — не більше однієї задачі за ітерацію. HTTP одразу відповідає
`202 {"jobId": N}`, клієнт опитує `GET /api/job?id=N`, поки статус не стане
`done`. Читання (`/api/wifi/status`, `/api/wifi/connections`) віддається з
готового знімка, який теж оновлює `loop()` — з тієї ж причини, плюс щоб не
тримати сире посилання на вектор, який інший таск може перевиділити.

## Статика: LittleFS, а під ним — прошивка

Ланцюжок `CompositeStaticSource`:

1. `LittleFS:/www` (пріоритет 100) — оновлюється через `pio run -t uploadfs`;
2. вшита gzip-копія в PROGMEM (пріоритет −100).

Другий рівень існує тому, що LittleFS буває порожнім: чиста плата або щойно
виконаний `uploadfs`, який переписує розділ цілком. Без вшитої копії пристрій,
що не бачить жодної мережі, не можна було б налаштувати навіть з його власної
точки доступу.

Джерело сторінки одне — `data/www/index.html`. Після кожної правки:

```sh
./tools/gen_web_assets.py     # перегенерувати lib/WebPortal/WebPortalAssets.hpp
pio run -t uploadfs -e esp32-c6   # залити оновлену версію в LittleFS
```

Згенерований заголовок комітиться, тож збірка не потребує Python.

## Доступ

HTTP Basic, логін і пароль у NVS (ключі `web_user` / `web_pass`). Поки пароль
не заданий, портал відкритий — інакше перша ж прошивка залишила б пристрій
без доступу до власного налаштування.

```
web                         # статус порталу і адреса
web auth admin s3cret       # задати креденшели
web auth off                # вимкнути автентифікацію
```

Зміна застосовується після перезавантаження: middleware додається в
`HttpServer::begin()`.

## API

| Метод | Шлях | Дія |
|---|---|---|
| GET | `/api/status` | uptime, heap, чи ввімкнена авторизація, список розділів |
| GET | `/api/job?id=N` | результат задачі: `queued` / `running` / `done` / `expired` |
| POST | `/api/auth` | `user`, `password` — змінити креденшели |
| GET | `/api/wifi/status` | стан FSM, SSID, IP, RSSI, точка доступу |
| GET | `/api/wifi/connections` | збережені профілі (без паролів) |
| POST | `/api/wifi/connections` | `ssid`, `password`, `priority`, `enabled`, `connect` |
| DELETE | `/api/wifi/connections?id=N` | видалити профіль |
| POST | `/api/wifi/connect` | `id` — підключитись до профілю |
| POST | `/api/wifi/scan` | скан ефіру (задача) |
| POST | `/api/wifi/hotspot` | `action=start\|stop` |
| POST | `/api/wifi/reconnect` | повний перебір мереж заново |
| GET | `/api/console/log?since=N` | рядки логу з номера N |
| GET | `/api/commands/list` | список зареєстрованих serial-команд (ім'я + опис) |
| POST | `/api/commands/exec` | `cmd` — покласти команду в `CommandQueue`; 202 `{"queued":…}` або **503**, якщо черга повна |
| GET | `/api/commands/shortcuts` | збережені shortcuts (`index`, `name`, `command`) |
| POST | `/api/commands/shortcuts` | `name`, `command`, опційно `index` — зберегти або перезаписати (задача) |
| DELETE | `/api/commands/shortcuts?index=N` | видалити shortcut (задача) |

Тіла запитів — `application/x-www-form-urlencoded`, відповіді — JSON.

## Консоль: що в неї потрапляє

Два шляхи, обидва курсорні по тому самому `seq`:

| Ендпойнт | Що це |
|---|---|
| `GET /api/console/stream` | SSE, основний. Кадр несе `id: <seq>`; при обриві браузер перепідключається сам і надсилає `Last-Event-ID` |
| `GET /api/console/log?since=<seq>` | опитування, відкат. Лишається, бо SSE через AP-режим або кепський лінк може не піднятись |

> **Перевірка SSE з `curl` вимагає заголовка.**
> `curl -N http://<ip>/api/console/stream` віддає **`Not found`** — не тому, що
> ендпойнта немає, а тому що `AsyncEventSource` береться за запит лише за
> наявності `Accept: text/event-stream`. Браузер шле його сам:
>
> ```sh
> curl -N -H "Accept: text/event-stream" http://192.168.1.111/api/console/stream
> ```

Сторінка тримає один `logCursor` на обидва, тому перемикання туди-сюди не дає
ні дублів, ні дірок. Поточне джерело видно в заголовку «Log»: `live (SSE)` або
`polling (AJAX)`; після трьох невдалих спроб поспіль сторінка перестає піднімати
потік і лишається на опитуванні — індикатор стає кнопкою «click to retry SSE».

> **Опитувальники не накладаються.** Кожен періодичний запит планується
> `setTimeout`-ом ПІСЛЯ того, як завершився попередній, а не `setInterval`-ом.
> Через `setInterval` вкладка на слабкому лінку накопичувала десятки
> одночасних `fetch`-ів з тим самим `?since=` — плата не встигала відповідати,
> а сторінка сипала ще й ще, і потік SSE в цій тисняві не піднімався взагалі.
> Плюс: при збоях період подвоюється (до ×8), у прихованій вкладці опитування
> не йде, а стан Wi-Fi опитується лише поки відкрита його вкладка. Список
> профілів по таймеру не тягнеться взагалі — лише при відкритті вкладки й після
> дій, що його змінюють.

> **Пастка `AsyncEventSource`, яка коштувала пів дня.** `_addClient()` бере
> `std::mutex` списку клієнтів і кличе `onConnect`, не відпустивши його. Мьютекс
> не рекурсивний — тому виклик `count()`, `avgPacketsWaiting()` чи `send()`
> **із цього колбека** вішає таск AsyncTCP на самого себе, і сервер перестає
> приймати нові з'єднання, поки відкритий бодай один SSE-клієнт. Пристрій при
> цьому пінгується — саме тому симптом і збиває з пантелику. З `onConnect`
> можна лише читати свій стан; надсилає `loop()`.

Власного буфера консоль **не має**: `/api/console/log` читає кільце журналу
(`lib/Journal`) напряму, за тим самим наскрізним `seq`. Тобто в браузері видно
записи з **усіх** тасків — те саме, що в serial-моніторі й у MQTT-дзеркалі
(`lib/ConsoleMqtt`), в одному порядку.

Обмеження: у журнал потрапляє лише те, що йде через `Logger`/`TLogger`.
Прямі `Serial.print*` у веб-консолі не з'являться.

Глибина історії = розмір кільця, `JOURNAL_RING` (32 на `esp32-c6*`/`esp32-c3`,
див. `platformio.ini`). Якщо клієнт відстав більше, він бачить це з поля `from`
у відповіді — сторінка показує явний рядок про втрачені рядки замість того, щоб
вдавати безперервність.

> До етапу 4 рефактора (`docs/journal_plan.md`) поруч жив `WebLogBuffer` —
> копія тих самих рядків із власною нумерацією, `WEB_CONSOLE_LINES` (60) по 160
> байтів, 9.6 КБ у `.bss`. Кільце зберігало те саме, тому копія була чистим
> дублюванням і видалена. Ціна: глибина впала з 60 рядків до 32, і залповий
> вивід (`list` — 70 рядків) браузер побачить із розривом. Лікується одним
> числом — `-D JOURNAL_RING=64` в env (5.9 КБ RAM за глибину 64).

## Розділ «Команди»

Три речі на одній вкладці: перелік зареєстрованих команд із фільтром, поле
запуску з аргументами і shortcuts.

**Запуск — один вхід на весь портал.** `POST /api/commands/exec` — єдиний
маршрут «виконати рядок»; поле вводу консолі шле свій рядок туди ж, власного
`/api/console/exec` більше немає. Дві копії розійшлись би на першій же зміні
валідації, і це саме той випадок, про який попереджає `CLAUDE.md`.

Команда не виконується в таску сервера: вона лягає в `CommandQueue`, той самий
вхід, що для serial, MQTT і cron, а виконує її `loop()`. Тому відповіді
«готово» немає й бути не може — результат приїжджає рядками в стрічку логу,
яку читає вкладка Console. Черга скінченна, відмова явна: **503**.

**Панель Output** на цій же вкладці — та сама стрічка журналу, лише від
запуску команди й до її кінця. Другого каналу на пристрої для цього НЕ
зроблено, і це свідомо: вивід уже їде до браузера одним потоком (SSE), а
другий шлях «доставити рядок» означав би ще один буфер у RAM і ще один
ендпойнт опитування.

Кінець приходить у самій стрічці. `CommandQueue::runNow()` друкує парний до
луни рядок **`< <команда> (N ms)`** (тег `cmd`) після того, як команда
відпрацювала — для КОЖНОЇ команди, звідки б вона не прийшла. Сторінка звіряє
текст команди в позначці зі своїм і на цьому перестає дописувати панель:
інакше під заголовком нашої команди накопичувався б фон — крон, телеметрія,
мережеві події. Консоль, навпаки, показує все як і раніше.

Рядок позначки йде **після** `CommandResponse::finish()`: у відповідь на MQTT
чи в лист має піти рівно вивід команди, без службової позначки.

Що лишилось неідеальним і чому це прийнятно:

- чужі рядки, які вклинились ДО кінця команди, в панелі лишаються — вони
  справді були в стрічці, поки команда працювала, і в serial видно те саме;
- якщо позначка не прийде взагалі (`reboot`, обрив стрічки), збирання
  зупиняється за таймаутом 60 с із чесним написом `stopped: no end marker`.

**Shortcuts** — вільний список «назва + рядок команди». Лежать у NVS одним
ключем `web_shortcuts` (`ConfigStorage::setStringArray()`), елемент —
`<назва>\t<команда>`: табуляція замість JSON, щоб не тягнути парсер на
пристрій заради двох полів. Її ж і забороняє валідація — інакше запис
розʼїхався б при наступному читанні. Стеля — `WEB_COMMANDS_MAX_SHORTCUTS`
(16): усе лежить одним блобом, який читається й пишеться цілком.

Запис у flash — через `WebJobQueue`, як і будь-яка інша мутація. Читання —
з готового знімка JSON: сам вектор чіпає лише `loop()`, а таск сервера бачить
рядок під мьютексом (та сама схема, що в `WebWifiModule`).

> **Чому `/api/commands/list`, а не `/api/commands`.**
> `AsyncCallbackWebHandler::canHandle()` вважає свій uri **префіксом**:
> `_uri != request->url() && !request->url().startsWith(_uri + "/")`
> (`WebHandlers.cpp:294`). Маршрут `/api/commands` тому перехоплював і
> `GET /api/commands/shortcuts` — на залізі той віддавав список команд, і
> мовчки: обидві відповіді валідний JSON. Метод рятує лише частково
> (`POST /api/commands/exec` не збігався з GET-переліком і працював). Правило:
> **жоден шлях розділу не може бути префіксом іншого шляху того ж розділу.**

Перелік команд, навпаки, віддається прямо з `SerialCommander` без знімка:
реєстр наповнюється в `setup()` і далі не міняється. Фільтр працює в браузері
— запит на кожну натиснуту літеру заради двох десятків рядків платі не
потрібен.

## Пастка, на яку вже наступили: ODR-колізія імен класів

Перша робоча збірка віддавала **404 на всю статику**, хоча обробник
реєструвався, джерела були на місці, а `/api/*` працювали. Причина: клас
звався `StaticRequestHandler`, і рівно так само зветься внутрішній клас
вбудованої в arduino-esp32 бібліотеки `WebServer`
(`libraries/WebServer/src/detail/RequestHandlersImpl.h`), яка потрапляє в
збірку разом із `lib/SDImageServer`.

Обидва класи лежали в глобальному namespace, тому мали однакове манглене ім'я
vtable (`_ZTV20StaticRequestHandler`). Лінкер не впав — він мовчки лишив одну
таблицю, чужу. Об'єкт створювався нашим конструктором, а `canHandle()`
викликався з core-класу (інша сигнатура, той самий слот у vtable) і завжди
повертав `false`. У наш код виконання просто не заходило, тому й діагностичні
логи в ньому мовчали.

Видно це було в `firmware.map`: символ `StaticRequestHandler::StaticRequestHandler(fs::FS&, ...)`
з `WebServer.cpp.o` — конструктор із сигнатурою, якої в нашому класі немає.

Клас перейменовано на `StaticSourceHandler`. Це та сама стратегія, через яку
обгортка зветься `HttpServer`, а не `WebServer`. Перед додаванням нового
публічного класу в `lib/` варто перевіряти ім'я:

```sh
grep -rl "class <Name>\b" \
  ~/.platformio/packages/framework-arduinoespressif32/libraries \
  .pio/libdeps/<env>
```

## Ціна

Заміряно 15.09.2026 на **всіх семи env, де портал увімкнений** — `pio run -e <env>`
з `PLATFORMIO_BUILD_FLAGS="-D HAS_WEB_PORTAL=0"` і без нього. Числа включають
розділ «Команди».

> **Відсоток, який друкує `pio`, тут не показник.** Він рахується від повного
> флешу плати (`board_upload.maximum_size`), а не від app-розділу: на
> `esp32-c6` це 8 МБ проти реальних 2 МБ, тобто «23% використано» насправді
> означає 93%. Колонка «вільно» нижче рахована як
> `<app size з partitions_*.csv> − used`.

| env | app-розділ | Δ флеш | Δ статична RAM | вільно після | запас |
|---|---:|---:|---:|---:|---:|
| `esp32-4848s040` ¹ | 4.00 МБ | +69.9 КБ | +928 Б | 2 391 757 | 57.0% |
| `esp32-c6` | 2.00 МБ | +68.8 КБ | +936 Б | **135 738** | **6.5%** |
| `esp32-c6-lcd096` | 2.00 МБ | +59.3 КБ | +936 Б | 319 018 | 15.2% |
| `esp32-st7789` | 1.89 МБ | +59.3 КБ | +952 Б | 319 270 | 16.1% |
| `ttgo-t1` | 3.00 МБ | +57.6 КБ | +960 Б | 1 632 745 | 51.9% |
| `esp32-c3` | 2.00 МБ | +57.4 КБ | +936 Б | 512 633 | 24.4% |
| `esp32-s3-lcd147` | 3.00 МБ | +56.2 КБ | +936 Б | 1 459 486 | 46.4% |

¹ `esp32-4848s040` збирається в `build_type = debug`, звідси найбільший приріст.

**Найтісніше на `esp32-c6`** — 135 КБ вільних у 2-мегабайтному app-розділі
(6.5%). Це не про портал: там просто найбільший набір фіч (SD, EcoFlow, Gmail,
дисплей). Але наступні розділи порталу (CRUD LittleFS, NVS, екран) міряти
треба саме по ньому, а не по платі, що лежить на столі.

**Що додав розділ «Команди»:** на `esp32-c6` було +58.3 КБ, стало +68.8 КБ,
тобто **+10.5 КБ флешу** — приблизно порівну модуль (`WebCommandsModule`,
маршрути й складання JSON) і вшита сторінка, gzip якої виріс із 7 349 до
10 221 Б. Статична RAM не змінилась: shortcuts живуть у NVS, а в `.bss` від
них лише порожній `std::vector` і рядок знімка.

До рефактора журналу (`docs/journal_plan.md`) статична RAM порталу була
**+10.4 КБ**: консоль носила власний буфер `WebLogBuffer` (60 × 160 Б). Тепер
вона читає кільце, і від порталу лишається менше кілобайта статики.

Скрипт заміру (щоб не збирати руками сім разів):

```sh
for e in esp32-4848s040 esp32-c3 esp32-c6 esp32-c6-lcd096 \
         esp32-s3-lcd147 esp32-st7789 ttgo-t1; do
  on=$(pio run -e "$e" 2>&1 | grep -oP "Flash: .*used \K[0-9]+")
  off=$(PLATFORMIO_BUILD_FLAGS="-D HAS_WEB_PORTAL=0" pio run -e "$e" 2>&1 \
        | grep -oP "Flash: .*used \K[0-9]+")
  echo "$e $(( (on - off) / 1024 )) KB"
done
```

**Дивитись треба не на флеш, а на купу.** Вільного місця в app-розділі
вистачає скрізь із запасом, а от heap портал витрачає в рантаймі: таск
AsyncTCP плюс буфери на кожне з'єднання (`HttpServerConfig::maxClients` = 4).
На платах без PSRAM це і є обмежувач, і він уже дав наслідок:

> **На `esp32-st7789` і `ttgo-t1` портал витіснив EcoFlow.** TLS-сесія EcoFlow
> потребує ~57 КБ **одним блоком**, а з піднятим порталом найбільший вільний
> блок падає до 32.7 КБ на обох платах (без портала — 59.4 і 69.6 КБ, і тоді
> EcoFlow конектиться). Вибрано портал, `HAS_ECOFLOW_CLIENT` на цих двох платах
> знято. Таблиця замірів — `docs/architecture.md`, виноска ⁸; спроби помістити
> обидва — `docs/optimization_backlog.md`, пункт 3.

Перевірено на залізі 15.09.2026 — `esp32-st7789` і `ttgo-t1`, обидві без PSRAM:
сторінка з LittleFS (20 022 Б),
SSE, запуск команди з браузера (тоді ще `POST /api/console/exec`), шість циклів підключення/відключення SSE і
трихвилинний профіль «відкрита вкладка» витоку не дали — `free` тримається на
64 КБ. Що змінюється — це фрагментація: `largest block` після сеансу зі
сторінкою сповзає з 63 до 39 КБ і назад сам не повертається.

## Що перевірено на залізі

`esp32-c6-lcd096`, підключення до домашньої мережі:

- статика з LittleFS (`14 093 B`) і, після заливки образу без `/www`, вшитий
  fallback (`5 086 B`, `Content-Encoding: gzip`) — обидва віддаються;
- `/api/wifi/status`, `/api/wifi/connections`, скан ефіру через чергу задач
  (знайшов 4 мережі, позначки `inUse`/`known` коректні);
- запуск serial-команди з веб-консолі (`status littlefs`) і поява її виводу
  в стрічці логу; курсор `?since=` працює;
- HTTP Basic: без креденшелів і з хибними — `401`, з вірними — `200`, і на
  API, і на статиці.

Розділ «Команди», 15.09.2026, та сама плата (частина — у браузері):

- `/api/commands/list` — 70 команд; фільтр на сторінці показує `2 of 70` на
  слово `wifi`;
- shortcut збережено, перезаписано й видалено; неіснуючий індекс —
  `{"ok":false,"message":"No such shortcut"}`; порожні `name`/`command` — `400`;
- shortcuts **пережили `uploadfs`** — вони в NVS, а стирається LittleFS;
- `POST /api/commands/exec` з `cmd=heap` → `202`, у стрічці `[I][web] > heap`,
  вивід команди й позначка `[I][cmd] < heap (301 ms)`;
- панель Output зупинилась рівно на цій позначці: далі 10 с фонових рядків
  (ecoflow, time sync) у неї не потрапило, а в консолі вони є;
- `POST /api/console/exec` — `404` (маршруту більше немає).

**Пастка, яку зловили саме тут:** до перейменування `GET /api/commands` віддавав
список команд і на `/api/commands/shortcuts` — див. врізку про префіксний матч
вище.
