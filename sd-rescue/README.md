# sd-rescue — порятунок даних з деградованої SD картки

Інструменти для витягування даних з SD картки, яку **не бачить хост-комп'ютер,
але читає плата ESP32**. Написані під конкретний випадок (див. «Діагноз»), але
придатні для будь-якої картки з подібними симптомами.

## Діагноз, під який це зроблено

Картка 256 ГБ з rootfs Raspberry Pi OS (MBR: FAT32 512 MiB + ext4 232 GiB,
з них 50.7 GiB даних). Комп'ютер картку не визначає; ESP32 читає.

Ключове: **биті сектори відсутні**. Деградувала сама flash-пам'ять — частина
клітинок втратила заряд і читається то як 0, то як 1. Симптоми:

- різниця між двома читаннями того самого місця — завжди **рівно один біт**;
- **CRC16 SD-протоколу проходить**, тому ні ядро, ні `dd` помилок не бачать;
- не залежить від частоти SPI (перевірено 400 кГц, 4 МГц, 40 МГц), від
  розміру пачки та від пауз між читаннями;
- градієнт по картці: ~6% нестабільних ділянок на початку rootfs, 15% на
  boot-розділі, до 40% у хвості.

**Мажоритарне голосування тут не працює.** Істинне значення байта трапляється
*рідше* за помилкове (заміряно: правильний байт випав 7 разів із 50). Тому
відновлення будується не на статистиці, а на **контрольних сумах ext4**:
перебір мерехтливих бітів до збігу csum дає точний результат. Так відновлено
402 з 1860 дескрипторів груп; 456 груп (усі в хвості картки) втрачено
незворотно — там біти перевернуті стабільно.

Що збереглося добре: inode-таблиці (99.85% валідних csum) і блоки каталогів
(~90%). Побитий саме кореневий каталог — його вміст відновлено інакше:
номери inode підтверджуються записом `..` дитини (має дорівнювати 2), а імена
виправляються за мінімальною бітовою відстанню до стандартних імен Linux.

## Інструменти

Усі читають **образ** (`~/sd-rescue/card.img`) за замовчуванням, тому не
заважають зніманню й працюють, поки imager іде. Джерело можна змінити
(`--source /dev/sda` або URL HTTP-сервера плати).

### Перегляд і витягування даних

| Скрипт | Що робить | Як запускати |
|---|---|---|
| `imgstat.py` | Що вже є в образі: скільки шматків знято, які структури ext4 на місці, **готовність метаданих** у відсотках | `imgstat.py`<br>`imgstat.py <образ>` |
| `walk_tree.py` | Обходить дерево каталогів і будує `tree.jsonl` (шлях, inode, тип). Читає лише метадані | `walk_tree.py`<br>`walk_tree.py ~/sd-rescue/card.img` |
| `showtree.py` | Перегляд дерева з `tree.jsonl` — миттєво, без читання образу. `--ready` додає готовність файлів | `showtree.py`<br>`showtree.py /etc --depth 2`<br>`showtree.py --find passwd`<br>`showtree.py /home/nick/Work --ready` |
| `catfile.py` | Один файл: вивести, зберегти або перевірити готовність. Не бреше про те, чого ще немає в образі | `catfile.py /etc/fstab`<br>`catfile.py /etc/fstab --out ./fstab`<br>`catfile.py /path --check` |
| `extract.py` | Масове витягування тек у `~/sd-rescue/`, з `_manifest.jsonl` (статус кожного файлу: clean / suspect / partial) | `extract.py /etc /root`<br>`extract.py /home/nick --dest ~/save` |

### Знімання образу

| Скрипт | Що робить | Як запускати |
|---|---|---|
| `imager.py` | **Головний інструмент.** Знімає образ з resume і картою достовірності. Копіює лише зайняте (за `occupied.bin`) | `imager.py --source /dev/sda --out ~/sd-rescue/card.img --single-pass` |
| `imager_watchdog.sh` | Сторож: перезапускає imager після падінь. Можна запускати будь-коли — бачить працюючий imager і чекає | `nohup ./imager_watchdog.sh &` |
| `dash.py` | Дашборд: **стан пристрою** (ознаки залипання картки), фаза, швидкість, ETA, чи не зависло | `dash.py`<br>`dash.py -w` (оновлення щосекунди) |
| `read_bitmaps.py` | Карта зайнятих блоків ФС → `occupied.bin`. Без неї imager копіював би всі 233 GiB замість ~124 | `read_bitmaps.py /dev/sda` |

### Відновлення метаданих і діагностика

| Скрипт | Що робить | Як запускати |
|---|---|---|
| `fix_gdt.py` | Відновлює дескриптори груп перебором мерехтливих бітів до збігу crc32c → `gdt_fixed.bin` | `fix_gdt.py` (потребує `gdt1..9.bin`) |
| `find_root2.py` | Відновлює вміст кореневого каталогу через перевірку `..` кандидатів | `find_root2.py ~/sd-rescue/card.img` |
| `scan_inodes.py` | Сканує inode-таблиці всіх груп → `inodes.jsonl`. Дає перелік вмісту навіть при побитих каталогах | `scan_inodes.py /dev/sda` |
| `sdcmd.py` | Надсилає команду в SerialCommander плати (порт визначає сам) | `sdcmd.py "sdmsc on"`<br>`sdcmd.py "sdverify 1056768 1024 64 3"` |
| `setfreq.py` | Змінює `SD_FREQ` у `[env:esp32-c6]` для експериментів з частотою шини | `setfreq.py 20000000` |

### Типовий порядок роботи

```bash
# 1. Підняти канал: картка як USB-диск (плата esp32-s3-lcd147)
python3 tools/sdcmd.py "sdmsc on"

# 2. Карта зайнятих блоків (один раз)
python3 tools/read_bitmaps.py /dev/sda

# 3. Знімання образу + сторож + спостереження
nohup ./tools/imager_watchdog.sh &
python3 tools/dash.py -w            # в іншому терміналі

# 4. Поки знімається - дивитись, що вже доступно
python3 tools/imgstat.py                          # готовність метаданих
python3 tools/walk_tree.py ~/sd-rescue/card.img   # дерево (перезапускати)
python3 tools/showtree.py /etc --ready            # готовність файлів теки
python3 tools/catfile.py /etc/fstab               # вміст файлу
python3 tools/extract.py /etc /root               # витягнути готове

# 5. Коли образ знято повністю
e2fsck -fy ~/sd-rescue/card.img     # через losetup, див. imgstat.py
```

## Прошивка плати

Інструменти спираються на serial-команди та сервери, реалізовані в цьому ж
репозиторії:

- `lib/SDRawReader/` — читання секторів в обхід ФС; `SdBulkReader` містить
  спільні алгоритми (замір швидкості, перевірка повторюваності, карта
  деградації, читання з голосуванням), `SdSpiBulkReader` і `SdMmcBulkReader` —
  лише доступ до заліза;
- `lib/SDImageServer/` — HTTP-сервер, що віддає картку як `/sd.img` з Range
  (сумісний з `qemu-nbd`);
- `lib/SdMassStorage/` — на `esp32-s3-lcd147` плата віддає картку хосту як
  **USB-накопичувач read-only**, і тоді працюють штатні `ddrescue`/`e2fsck`.

Команди: `sdraw`, `sdext4`, `sdbench`, `sdcrc`, `sdverify`, `sdmap`,
`sdimg on|off|status`, `sdmsc on|off|status` (S3).

## Порядок роботи

```bash
# 1. Стан ФС і скільки даних реально є
sdext4 2                      # на платі, через serial

# 2. Наскільько картка деградувала
sdmap 0 488554496 200 8 3     # карта: '.' надійно, 'x' мерехтить, 'E' не читається

# 3. Канал до хоста
sdmsc on                      # S3: картка з'явиться як /dev/sdX  (варіант без WiFi)
sdimg on                      # C6: http://<ip>:8080/sd.img

# 4. Карта зайнятих блоків і образ
python3 tools/read_bitmaps.py
python3 tools/imager.py --source /dev/sdX --out ~/sd-rescue/card.img
python3 tools/dash.py -w      # в іншому терміналі

# 5. Лікування образу (картка не торкається!) і запис
e2fsck -fy card.img           # або на конкретний розділ через losetup
```

## Чого НЕ робити

- **Не писати на картку** й не запускати `fsck` на ній — тільки на копії.
  Журнал ext4 не доіграний, і будь-який запис може добити картку.
- **Не монтувати** розділ інакше як `-o ro,noload`: без `noload` ядро полізе
  відтворювати журнал, тобто писати.
- **Не довіряти голосуванню за більшістю** — на такій деградації воно дає
  систематично хибний результат (див. «Діагноз»).
